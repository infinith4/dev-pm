| 項目 | 内容 |

| **機能ID** | FR-011 |

### 概要

Azure マルチテナント環境において、テナント A のユーザーがテナント B のデータに物理的・論理的にアクセスできないことを保証する。採用モデルは **Bridge モデル**（共有アプリケーション + テナント専用 PostgreSQL DB）。多層防御（ルーティング層・アプリ層・DB 層）でデータ分離を実現する。

---

### 機能要件

---

**Isolation.Routing: テナントルーティングとコンテキスト確立**

**.Identify**: システムは、すべてのリクエストでテナント識別子をサブドメイン（`{tenant}.taskboard.jp`）または JWT クレーム（`tenant_id`）から抽出し、リクエストコンテキストに設定しなければならない。

**.Validate**: システムは、抽出したテナント ID が Platform DB に存在し、かつステータスが `active` または `trial` であることを検証しなければならない。検証に失敗した場合は HTTP 403 を返し、詳細情報を含まないエラーメッセージを表示しなければならない。

**.Middleware**: システムは、すべての API ルートにテナントコンテキスト検証ミドルウェアを適用しなければならない。ミドルウェアを適用除外した API エンドポイントを公開してはならない。（CO-6 参照）

**.APIKey**: Azure API Management は、各テナントに発行した API キーを検証し、キーに紐づくテナント ID をリクエストヘッダーに付与してバックエンドに転送しなければならない。

---

**Isolation.Database: データベース分離（Bridge モデル）**

**.Separate**: システムは、テナントごとに個別の PostgreSQL データベースまたはインスタンスを使用しなければならない。複数のテナントが同一データベースを共有してはならない。（BR-MT-01 参照）

**.ConnectionPool**: システムは、テナント ID をキーとして接続プールをキャッシュし、各リクエストのテナントコンテキストに対応した接続を選択しなければならない。

**.ConnectionValidation**: システムは、接続プールから取得した接続がリクエストのテナント ID と一致することを検証しなければならない。不一致の場合はリクエストを中断し、セキュリティインシデントとしてログに記録しなければならない。

**.NoDirectAccess**: テナント DB は Azure Private Endpoint 経由でのみアクセスを許可し、パブリック IP からのアクセスを拒否しなければならない。（BR-MT-04 参照）

**.ConnectionString**: テナント DB 接続文字列はアプリケーションコード・環境変数・ログに含めてはならない。Azure Key Vault への参照 URI のみを Platform DB に保存する。（BR-MT-02 参照）

---

**Isolation.Storage: ストレージ分離**

**.Container**: システムは、テナントごとに個別の Azure Blob Storage コンテナを使用しなければならない（命名規則: `tenant-{tenant_id}`）。

**.SAS**: ファイルアクセスには Shared Access Signature（SAS）トークンを使用し、トークンはリクエストごとに生成する。SAS の有効期限は 1 時間以内とする。（BR-MT-05 参照）

**.CrossTenantBlock**: システムは、テナント A のユーザーがテナント B のコンテナ URL を直接指定してアクセスできないことを保証しなければならない。

---

**Isolation.API: API 層での分離保証**

**.TenantScope**: すべての API レスポンスは、リクエストのテナントコンテキストに属するデータのみを含まなければならない。

**.AdminScope**: プラットフォーム管理者 API は専用エンドポイント（`/admin/`）に分離し、通常テナントユーザーがアクセスできないようにしなければならない。

**.ErrorMessage**: テナント分離違反が疑われるリクエストへのエラーレスポンスは、テナント ID・DB 接続情報・内部エラー詳細を含めてはならない。HTTP 403 と汎用エラーメッセージのみを返す。

**.RateLimit**: Azure API Management は、テナントごとに API レート制限を適用しなければならない（Starter: 100 req/分、Professional: 500 req/分、Enterprise: 2,000 req/分）。（BR-MT-50 参照）

---

**Isolation.Audit: 監査・検出**

**.AccessLog**: システムは、すべての API リクエストにテナント ID・ユーザー ID・エンドポイント・レスポンスコード・処理時間を記録し、Azure Monitor に送信しなければならない。

**.AnomalyAlert**: システムは、1 リクエスト内で複数のテナント ID へのアクセス試行を検出した場合、プラットフォーム管理者にリアルタイムアラートを送信しなければならない。

**.PenTest**: システムは、リリース前にテナント分離を対象とするペネトレーションテスト（外部業者による）を実施し、合格しなければならない。（SM-3 参照）

**.RetentionLog**: 監査ログは 2 年間保持しなければならない。（BR-MT-41 参照）

---

### テナント分離の多層防御モデル

```
[Layer 1: ネットワーク層]
  Azure Front Door → サブドメインでテナントを識別
  Azure API Management → API キー検証・レート制限・テナント ID ヘッダー付与

[Layer 2: アプリケーション層]
  テナントコンテキスト検証ミドルウェア（全エンドポイント適用）
  JWT クレームの tenant_id 検証
  レスポンスフィルタリング（テナントスコープのみ返却）

[Layer 3: データベース層]
  テナント専用 PostgreSQL DB（物理分離）
  接続プールのテナント ID 一致検証
  Azure Private Endpoint（パブリックアクセス拒否）

[Layer 4: ストレージ層]
  テナント専用 Blob コンテナ
  SAS トークン（1時間有効）によるアクセス制御
  RBAC でコンテナ間アクセスを禁止

[Layer 5: 監査層]
  全リクエストの Azure Monitor ログ
  異常アクセスのリアルタイムアラート
  定期ペネトレーションテスト
```

---

### 例外・エラー処理

| ケース | 条件 | システムの応答 |
|-------|------|-------------|
| テナント ID 不一致 | JWT の tenant_id とルーティングのテナントが不一致 | HTTP 403 を返却。セキュリティインシデントとしてログに記録し、管理者にアラートを送信する |
| 存在しないテナント | URL のサブドメインが Platform DB に存在しない | HTTP 404（テナントが存在しないことを示す情報は含めない） |
| 停止中テナント | テナントのステータスが `suspended` | HTTP 403 と「このアカウントは停止されています。管理者にお問い合わせください」を表示する |
| 接続文字列取得失敗 | Key Vault からの接続文字列取得が失敗した | HTTP 503 を返却。リトライ処理（3回）後も失敗する場合はプラットフォーム管理者にアラートを送信する |
