# 非機能要件定義書 (NFR)
## TaskBoard SaaS ─ Azure マルチテナント

> **参考**: Karl Wiegers "Software Requirements 3rd Edition" Chapter 14 "Beyond Functionality"
>
> **設計指針（Wiegers Chapter 14 より）**:
> - 品質属性は「外部品質」（ユーザーが実行時に識別できる）と「内部品質」（開発・保守担当者が重視する）に分類する。
> - 品質属性が競合する場合（例: セキュリティ強化によるパフォーマンス低下）、優先度を明示して設計の判断基準にする。
> - マルチテナント SaaS では **セキュリティ > 可用性 > スケーラビリティ > パフォーマンス** の優先順位を基本とする。

## 1. 品質属性の優先順位

> Wiegers が推奨する品質属性優先度分析（Chapter 14）を実施し、以下の順位を決定した。

| 順位 | 品質属性 | スコア | 理由 |
|------|---------|-------|------|
| 1 | **セキュリティ（Security）** | 9 | テナント間データ漏洩は事業継続の根幹を損なう。0 件必達（SM-3）。 |
| 2 | **可用性（Availability）** | 8 | SaaS は常に稼働していることが前提。SLA 99.9% 必達。 |
| 3 | **スケーラビリティ（Scalability）** | 7 | テナント数・ユーザー数の増加への対応がビジネス成長に直結する。 |
| 4 | **信頼性（Reliability）** | 7 | データ損失は顧客信頼を失う。RPO 5 分必達。 |
| 5 | **パフォーマンス（Performance）** | 6 | レスポンス低下はユーザー離脱に直結するが、セキュリティと競合する場合はセキュリティを優先する。 |
| 6 | **保守性（Maintainability）** | 5 | テナント数の増加に伴う運用自動化が必須。 |
| 7 | **ユーザビリティ（Usability）** | 4 | テナント管理者の初回設定体験が重要。エンドユーザーは既存 UX を継承。 |

## 2. セキュリティ（Security）― 優先度: 最高

> Wiegers: "Internet and corporate applications: security は必須の品質属性" (Chapter 14)

### 2.1 テナント分離

| 要件ID | 要件内容 | 検証方法 |
|-------|---------|---------|
| NFR-SEC-01 | テナント A の認証済みユーザーは、テナント B の任意のリソース（API / DB / ストレージ）にアクセスできないこと | ペネトレーションテスト（リリース前・外部業者実施） |
| NFR-SEC-02 | テナント DB 接続文字列はアプリケーションコード・ログ・環境変数に含まれてはならない | セキュリティコードレビュー・SAST ツール検査 |
| NFR-SEC-03 | すべての API エンドポイントにテナントコンテキスト検証を適用し、未検証のエンドポイントが存在しないこと | ルート一覧の網羅的レビュー・自動テスト |

### 2.2 認証・認可

| 要件ID | 要件内容 | 検証方法 |
|-------|---------|---------|
| NFR-SEC-10 | すべての API 呼び出しに有効な JWT（tenant_id・user_id・role クレーム含む）が必要であること | 認証テスト（無効トークン・期限切れトークン） |
| NFR-SEC-11 | JWT 有効期限: アクセストークン 1 時間、リフレッシュトークン 30 日（「ログインしたままにする」選択時）（BR-MT-20） | トークン検証テスト |
| NFR-SEC-12 | パスワードは bcrypt（コストファクター 12 以上）でハッシュ化して保存し、平文で保存・ログ出力してはならない | コードレビュー |
| NFR-SEC-13 | ログイン失敗 5 回でアカウントを 30 分ロックする（BR-MT-21） | 認証失敗テスト |
| NFR-SEC-14 | RBAC（ロールベースアクセス制御）を全 API で実施する。閲覧者は参照 API のみアクセス可能であること | 権限テスト（ロール別） |

### 2.3 通信・データ保護

| 要件ID | 要件内容 | 検証方法 |
|-------|---------|---------|
| NFR-SEC-20 | すべての通信を TLS 1.3 以上で暗号化すること（HTTP は HTTPS にリダイレクト） | SSL Labs テスト（評価 A 以上） |
| NFR-SEC-21 | 個人情報（氏名・メールアドレス・連絡先）は AES-256 で暗号化して保存すること | DB 暗号化設定確認 |
| NFR-SEC-22 | Azure Key Vault のシークレットは 90 日ごとに自動ローテーションすること | Key Vault ポリシー設定確認 |
| NFR-SEC-23 | OWASP Top 10 対策（SQL インジェクション・XSS・CSRF・Security Misconfiguration 等）を実装すること | OWASP ZAP による動的スキャン |
| NFR-SEC-24 | Stripe の Webhook は署名検証を行い、署名のないリクエストを拒否すること | Webhook テスト |

### 2.4 監査ログ

| 要件ID | 要件内容 | 検証方法 |
|-------|---------|---------|
| NFR-SEC-30 | 認証イベント（ログイン成功・失敗・ロック・SSO）を全件記録し、テナント ID・ユーザー ID・IP アドレス・タイムスタンプを含めること | ログ出力内容の確認 |
| NFR-SEC-31 | テナントデータの作成・更新・削除・エクスポートを全件記録すること | ログ出力内容の確認 |
| NFR-SEC-32 | 監査ログは改ざん防止のため Azure Monitor Logs（Immutable モード）に保存し、2 年間保持すること | Azure 設定確認 |

## 3. 可用性・信頼性（Availability & Reliability）― 優先度: 高

| 要件ID | 指標 | 要件値 | 測定方法 | 備考 |
|-------|------|-------|---------|------|
| NFR-AVL-01 | 月次稼働率（SLA） | ≥ 99.9%（月次ダウンタイム ≤ 43.8 分） | Azure Monitor の可用性メトリクス | 計画停止を除く |
| NFR-AVL-02 | RTO（目標復旧時間） | ≤ 1 時間 | 障害演習による実測 | テナント全体の復旧 |
| NFR-AVL-03 | RPO（目標復旧時点） | ≤ 5 分 | バックアップ・リストアテスト | テナント DB の Point-in-Time Restore |
| NFR-AVL-04 | 計画停止ウィンドウ | 月 1 回・深夜 2:00〜4:00 JST・2 時間以内 | 事前通知必須（7 日前） | — |
| NFR-AVL-05 | テナント DB の自動バックアップ | 1 日 1 回（保持期間 35 日） | Azure PostgreSQL バックアップ設定確認 | Point-in-Time Restore 対応 |
| NFR-AVL-06 | テナント個別の障害が他テナントに影響しないこと | 1 テナントの障害影響範囲を当該テナントのみに限定 | 障害注入テスト（Chaos Engineering） | Noisy Neighbor 対策 |

## 4. パフォーマンス（Performance）― 優先度: 中

> セキュリティ層（テナントコンテキスト検証・接続プール切り替え）のオーバーヘッドを考慮した目標値。

| 要件ID | 指標 | 要件値 | 測定方法 | 備考 |
|-------|------|-------|---------|------|
| NFR-PRF-01 | API レスポンスタイム（95%ile） | ≤ 300ms | Azure Application Insights / Load Test | テナント DB ルーティングオーバーヘッド込み |
| NFR-PRF-02 | 画面初期表示（Core Web Vitals LCP） | ≤ 2.5 秒 | Lighthouse / WebPageTest | CDN キャッシュ活用 |
| NFR-PRF-03 | テナントプロビジョニング時間 | ≤ 3 分 | プロビジョニングログのタイムスタンプ差分 | メール確認完了から利用開始まで |
| NFR-PRF-04 | 同時接続テナント数 | ≥ 100 テナント（Release 1） | 負荷テスト（各テナント 10 ユーザー同時） | — |
| NFR-PRF-05 | テナントあたりの同時ユーザー数 | ≥ 50 ユーザー（Starter）、≥ 200（Professional）、≥ 500（Enterprise） | 負荷テスト | — |

## 5. スケーラビリティ（Scalability）― 優先度: 高

| 要件ID | 指標 | 要件値 | 備考 |
|-------|------|-------|------|
| NFR-SCL-01 | アプリケーション層の水平スケール | CPU 使用率 70% 閾値で Auto Scaling を動作させること | Azure App Service Auto Scale ルール |
| NFR-SCL-02 | テナント数の上限 | Release 1 で 200 テナントまでパフォーマンス劣化なく動作すること | — |
| NFR-SCL-03 | テナント DB の追加 | 新テナント追加時に既存テナントのパフォーマンスに影響しないこと | Bridge モデルにより DB が独立 |
| NFR-SCL-04 | ストレージ容量 | テナントあたり Starter: 5GB、Professional: 50GB、Enterprise: 500GB を保証すること | — |

## 6. 保守性・運用性（Maintainability & Operability）― 優先度: 中

| 要件ID | 指標 | 要件値 |
|-------|------|-------|
| NFR-MNT-01 | テナントプロビジョニング・解約の手動手順 | 0 手順（完全自動化）。手動介入が必要な場合はアラートを発報する |
| NFR-MNT-02 | テナント別ログのフィルタリング | Application Insights でテナント ID によるログ・トレースの検索・フィルタリングが可能であること |
| NFR-MNT-03 | テナント DB スキーマのマイグレーション | 新リリース時に全テナント DB へのマイグレーションが無停止で適用できること（Blue-Green デプロイ） |
| NFR-MNT-04 | ユニットテストカバレッジ | テナント分離・認証・課金モジュールで ≥ 90%。全体 ≥ 80% |
| NFR-MNT-05 | インシデント対応 | P1（テナントデータ漏洩・全テナント停止）: 15 分以内に初動対応。P2（単一テナント障害）: 1 時間以内 |
| NFR-MNT-06 | 依存ライブラリの脆弱性スキャン | CI/CD パイプラインで Dependabot / Snyk による自動スキャンを実施し、Critical は 24 時間以内に対応する |

| 要件ID | 指標 | 要件値 |
|-------|------|-------|
| NFR-USB-01 | テナント管理者の初回設定完了時間 | サインアップからチームメンバー招待完了まで 10 分以内 |

## 8. コンプライアンス（Compliance）

| 要件ID | 法規制・基準 | 要件内容 |
|-------|-----------|---------|
| NFR-CMP-01 | 個人情報保護法 | 個人情報の収集・利用・第三者提供を法令に準拠した形で実装し、プライバシーポリシーを公開する |

## 9. 品質属性のトレードオフ

> Wiegers: "Quality attributes can clash" (Chapter 14) ─ 競合する品質属性の解決方針を明示する。

| 競合する属性 | 競合シナリオ | 解決方針 |
|-----------|-----------|---------|
| セキュリティ vs パフォーマンス | テナントコンテキスト検証・Key Vault 参照がレスポンスタイムに影響する | セキュリティを優先。接続プールキャッシュ・Key Vault の応答キャッシュ（TTL: 5 分）でパフォーマンスを補う |
| スケーラビリティ vs コスト | テナント数増加に伴いインフラ費用が増大する | Bridge モデル（DB per Tenant）を採用し、廉価プラン向けには将来 Pool モデルも提供する（Release 3） |
| 可用性 vs セキュリティ | 多層防御の追加により単一障害点が増加する | Azure の冗長化（Zone Redundant）と Key Vault の高可用性設定で対応する |
