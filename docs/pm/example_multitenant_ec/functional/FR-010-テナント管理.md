## 1. 概要

ShopHub SaaS のプラットフォーム管理者が、新規テナント（EC 事業者）のオンボーディングから停止・解約・削除までのライフサイクル全体を管理する機能を定義する。Microsoft Graph API を用いた Entra ID テナントの自動プロビジョニング、工場設定、課金プラン管理を含む。

**関連**:
- FE-1（テナント管理・Entra ID プロビジョニング）, FE-5（課金管理）
- BR-MT-01〜BR-MT-05, BR-MT-10〜BR-MT-13, BR-MT-30〜BR-MT-35, BR-MT-40〜BR-MT-42
- UC-002（店舗スタッフが管理サイトへ Entra ID SSO でログインする）
- US-010（テナントを登録する）

## 2. 機能要件

### 2.1 Tenant.Provision: テナント自動プロビジョニング

**Tenant.Provision.Register: テナント登録受付**

**.Form**: システムは、テナント管理者が企業名・スラッグ・代表メールアドレス・プラン選択を入力するサインアップフォームを提供しなければならない。

**.Verify**: システムは、登録後に代表メールアドレスへ確認メールを送信し、リンクのクリックをもって登録を完了しなければならない。

**.SlugValidation**: システムは、スラッグがプラットフォーム内で一意であることを確認し、英数字とハイフンのみ（3〜63 文字）を許可しなければならない。（BR-MT-10 参照）

**Tenant.Provision.Auto: 自動プロビジョニング処理**

**.EntraID**: システムは、Microsoft Graph API を使用してテナント専用の Entra ID テナントを自動作成しなければならない。（BR-MT-02 参照）

**.CIAM**: システムは、EC サイト用の Azure AD External Identities（CIAM）をテナントの Entra ID テナントに自動設定しなければならない。Google ソーシャルログインを標準で有効にする。（BR-MT-03 参照）

**.OIDCApp**: システムは、管理サイト用の OIDC アプリケーションをテナントの Entra ID テナントに自動登録し、`ShopHub.Admin` ロールを定義しなければならない。

**.Database**: システムは、テナント専用の Azure Database for PostgreSQL Flexible Server インスタンスを作成し、スキーマ初期化（マイグレーション実行）を行わなければならない。

**.Blob**: システムは、テナント専用の Azure Blob Storage コンテナ（`tenant-{tenant_id}`）を作成しなければならない。

**.Domain**: システムは、Azure Front Door にテナントのカスタムドメイン（`shop.{顧客ドメイン}` / `admin.{顧客ドメイン}`）を設定し、TLS 証明書を自動発行しなければならない。

**.KeyVault**: システムは、テナントの DB 接続文字列・API キーを Azure Key Vault に登録しなければならない。

**.Completion**: システムは、メール確認完了から 20 分以内にすべてのプロビジョニングを完了しなければならない。（BR-MT-01 参照）

**.Rollback**: システムは、プロビジョニング中にいずれかのステップが失敗した場合、作成済みリソースをすべて削除し、テナント状態を `provisioning_failed` に設定し、プラットフォーム管理者にアラートを送信しなければならない。（BR-MT-04 参照）

**.Trial**: システムは、プロビジョニング完了後に Stripe でトライアルサブスクリプション（14 日間、Professional プラン相当）を自動作成しなければならない。（BR-MT-30 参照）

### 2.2 Tenant.FactoryConfig: 工場設定

**Tenant.FactoryConfig.Register: 工場登録**

**.Add**: テナント管理者は、利用する工場（工場コード・工場名・フォーマット定義 ID・転送方式）を管理画面から登録できなければならない。

**.Limit**: システムは、Professional プランで最大 5 工場、Enterprise プランで無制限の工場登録を許可しなければならない。Starter プランでは工場登録を拒否しなければならない。（BR-MT-31 参照）

**.FormatDef**: テナント管理者は、工場ごとにフォーマット定義（列名・型・必須・マッピングルール・エンコーディング・区切り文字・ヘッダー有無）を設定できなければならない。（BR-FACTORY-01 参照）

**.SFTP**: 転送方式として SFTP を選択した場合、システムは SFTP ホスト名・ユーザー名・SSH 秘密鍵（Azure Key Vault 参照）の入力を要求しなければならない。（BR-FACTORY-07 参照）

**.Blob**: 転送方式として Azure Blob を選択した場合、システムは Blob URI の入力を要求しなければならない。

**.PGP**: テナント管理者は、工場ごとに PGP 暗号化の要否と PGP 公開鍵（Azure Key Vault に保存）を設定できなければならない。（BR-FACTORY-06 参照）

**.Notify**: テナント管理者は、工場ごとに転送完了通知方式（Webhook URL / メールアドレス / なし）を設定できなければならない。（BR-FACTORY-08 参照）

**Tenant.FactoryConfig.Update: 工場設定変更**

**.Update**: テナント管理者は、登録済みの工場設定（フォーマット定義・転送先・通知設定）を変更できなければならない。

**.ApplyNext**: フォーマット定義の変更は次回バッチ実行日から適用される。即時適用は手動バッチ再実行によって行う。（BR-FACTORY-10 参照）

**.AuditLog**: 工場設定の変更履歴は監査ログに記録しなければならない。（BR-FACTORY-10 参照）

### 2.3 Tenant.Config: テナント設定管理

**Tenant.Config.Basic: 基本設定**

**.Slug**: システムは、スラッグを一度設定したら変更できないようにしなければならない。（BR-MT-11 参照）

**.Domain**: テナント管理者は、カスタムドメイン（`shop.{顧客ドメイン}` / `admin.{顧客ドメイン}`）を設定できなければならない。Azure Front Door で CNAME を確認し、TLS 証明書を自動発行しなければならない。（BR-MT-12 参照）

**.Timezone**: テナント管理者は、テナントのタイムゾーンを設定できなければならない。（BR-MT-13 参照）

**Tenant.Config.Staff: スタッフロール管理**

**.Roles**: テナント管理者は、テナントの Entra ID テナントのロール（`ShopHub.Admin` / `ShopHub.Staff`）をスタッフユーザーに付与・剥奪できなければならない。

**.Invite**: テナント管理者は、メールアドレスを指定してスタッフを招待できなければならない。招待されたスタッフはテナントの Entra ID テナントにアカウントを作成してログインできるようになる。

### 2.4 Tenant.Lifecycle: テナントライフサイクル管理

**Tenant.Lifecycle.Suspend: テナント一時停止**

**.Suspend**: プラットフォーム管理者は、テナントを一時停止（`suspended`）状態にできなければならない。停止中はテナント管理者・店舗スタッフ・消費者のログインを拒否し、夜間バッチを停止する。

**.Resume**: プラットフォーム管理者は、停止中のテナントを再開（`active`）状態に戻せなければならない。

**Tenant.Lifecycle.Cancel: 解約**

**.Cancel**: テナント管理者は、Stripe サブスクリプションをキャンセルすることで解約できなければならない。解約後は次の課金サイクル終了までサービスを継続利用できる。

**.DataExport**: 解約前に、テナント管理者はすべてのテナントデータ（注文・商品・消費者情報・バッチログ・転送ログ）を CSV/JSON でエクスポートできなければならない。

**.DataRetention**: 解約後 90 日間、テナントデータを保持しなければならない。（BR-MT-40 参照）

**Tenant.Lifecycle.Delete: 物理削除**

**.Delete**: 90 日経過後、システムはテナントの PostgreSQL DB インスタンス・Blob コンテナ・Entra ID テナントを物理削除しなければならない。（BR-MT-41 参照）

**.AuditLog**: 物理削除のログを監査証跡として 7 年間保持しなければならない。（BR-MT-41 参照）

---

### 2.5 Tenant.Billing: サブスクリプション・課金管理

**Tenant.Billing.Plan: プラン管理**

**.Plans**: システムは、以下の 3 プランを提供しなければならない:
  - **Starter**: 月額 ¥30,000。EC サイト・管理サイト・Entra ID プロビジョニングのみ。夜間バッチ・工場連携は利用不可。
  - **Professional**: 月額 ¥80,000。Starter の全機能 + 夜間バッチ・工場連携（最大 5 工場）。
  - **Enterprise**: 月額 ¥200,000。Professional の全機能 + 工場連携無制限 + 優先サポート。
  （BR-MT-31 参照）

**.Upgrade**: テナント管理者はプランをアップグレードでき、差額は日割り計算されなければならない。アップグレードは即日適用する。（BR-MT-34 参照）

**.Downgrade**: テナント管理者はプランをダウングレードでき、次の課金サイクル開始時に適用されなければならない。夜間バッチが停止になる場合はテナント管理者に事前通知する。（BR-MT-35 参照）

**Tenant.Billing.Payment: 決済処理**

**.Card**: システムは Stripe を介してクレジットカード情報を登録・更新できなければならない。カード番号はシステム内に保存してはならない。（BR-MT-32 参照）

**.Invoice**: システムは月次で請求書を自動生成し、テナント管理者にメール送信しなければならない。

**.Failed**: 決済が失敗した場合、システムは 3 日間・3 回リトライし、最終失敗時にテナントを `payment_suspended` 状態に移行し、夜間バッチを停止しなければならない。（BR-MT-33 参照）

## 3. プロビジョニングフロー詳細

```
[Step 1] テナント管理者がサインアップフォームを送信
[Step 2] メールアドレス確認リンクのクリック
[Step 3] Platform DB にテナントレコード作成（status = provisioning）
[Step 4] Microsoft Graph API: Entra ID テナント自動作成
[Step 5] Entra ID テナントに CIAM（Azure AD External Identities）設定
[Step 6] Entra ID テナントに OIDC アプリ登録（管理サイト用）・ロール定義
[Step 7] Azure Database for PostgreSQL: テナント専用 DB 作成・スキーマ初期化
[Step 8] Azure Blob Storage: テナント専用コンテナ作成
[Step 9] Azure Front Door: カスタムドメイン設定・TLS 証明書発行
[Step 10] Azure Key Vault: 接続文字列・API キー登録
[Step 11] Stripe: トライアルサブスクリプション作成（14 日間、Professional 相当）
[Step 12] Platform DB: status = active に更新
[Step 13] テナント管理者にオンボーディング完了メール送信

所要時間: 20 分以内（BR-MT-01）
```
