## 1. 概要

消費者が商品を閲覧・カートに追加・Stripe 決済で購入できる EC サイト機能を定義する。テナントごとに専用の Azure AD External Identities（CIAM）で認証し、日次 1,000 万件（全テナント合計）の注文規模（ピーク時 10,000 req/sec）に対応する。

**主要コンポーネント**:
- 認証: Azure AD External Identities（CIAM）・ゲスト購入
- 商品検索: Azure Cognitive Search（テナント別インデックス）
- カート: Azure Cache for Redis（セッション管理）
- 決済: Stripe（クレジットカード決済）
- 注文管理: テナント専用 PostgreSQL DB

**関連**:
- FE-3（EC サイト）, FE-9（消費者認証 CIAM）
- BR-EC-01〜BR-EC-31
- UC-001（消費者が商品を購入する）
- US-001（消費者が商品を購入する）
- FR-020（夜間バッチの注文データソース）

## 2. ユーザークラスと特性

| ユーザークラス | 説明 | 利用頻度 | 優先度 |
|-------------|------|---------|-------|
| CIAM 認証済み消費者 | テナントの CIAM にサインアップ済みの消費者。注文履歴・カート引継ぎ可能。テナントあたり〜10 万名 | 日次 | Favored |
| ゲスト消費者 | CIAM アカウントなしで購入する消費者。メールアドレスのみ収集 | 随時 | Favored |

## 3. 機能要件

### 3.1 Shop.Auth: CIAM 認証（Azure AD External Identities）

**Shop.Auth.Login: ログイン**

**.Email**: システムは、テナント専用 CIAM のメールアドレス＋パスワードによるログインをサポートしなければならない。

**.Google**: システムは、Google アカウントによるソーシャルログイン（OAuth 2.0）をサポートしなければならない。（BR-EC-01 参照）

**.GuestCheckout**: システムは、CIAM アカウントなしのゲスト購入をサポートしなければならない。ゲスト購入時はメールアドレスのみを収集し、注文確認メールを送信しなければならない。（BR-EC-02 参照）

**.TenantIsolation**: システムは、ログイン処理においてテナントごとの CIAM を使用し、テナント A の消費者アカウントがテナント B の EC サイトに使用できないことを保証しなければならない。（BR-EC-01 参照）

**Shop.Auth.Register: 消費者登録**

**.Form**: システムは、メールアドレス・パスワード・氏名を入力する消費者登録フォームを提供しなければならない。

**.Verify**: システムは、消費者登録後にメールアドレス確認メールを送信し、リンクのクリックをもって登録を完了しなければならない。

**.Unique**: システムは、同一テナントの CIAM 内でメールアドレスの重複を拒否しなければならない。（BR-EC-03 参照）

**Shop.Auth.Session: セッション管理**

**.JWT**: システムは、CIAM からの JWT を検証し、セッションを確立しなければならない。

**.Redis**: システムは、セッションデータを Azure Cache for Redis に保存し、複数のアプリケーションノード間でセッションを共有しなければならない。

**.Logout**: システムは、ログアウト時にセッションデータを Redis から削除し、CIAM のセッションも終了しなければならない。

---

### 3.2 Shop.Browse: 商品カタログ・検索

**Shop.Browse.List: 商品一覧**

**.Catalog**: システムは、テナントが登録した商品（名称・価格・在庫状況・サムネイル画像）の一覧を表示しなければならない。在庫切れ商品はその旨を表示し、カートへの追加を不可にしなければならない。

**.Category**: システムは、商品をカテゴリでフィルタリングできなければならない。

**.Pagination**: システムは、商品一覧をページネーション（1 ページあたり 20〜100 件、選択可能）で表示しなければならない。

**Shop.Browse.Search: 商品検索**

**.FullText**: システムは、Azure Cognitive Search を使用して商品名・説明文での全文検索をサポートしなければならない。（テナント別インデックスを使用）

**.Suggest**: システムは、検索ボックス入力中にオートサジェスト（候補 5 件以上）を表示しなければならない。

**.Ranking**: システムは、検索結果を関連度スコアでランキングし、在庫切れ商品を下位に表示しなければならない。

**Shop.Browse.Detail: 商品詳細**

**.Detail**: システムは、商品詳細ページで商品名・価格・在庫数・説明文・商品画像（複数枚対応）を表示しなければならない。

**.Stock**: システムは、リアルタイムの在庫数を商品詳細ページに表示しなければならない。

---

### 3.3 Shop.Cart: カート管理

**Shop.Cart.Add: カートへの追加**

**.Add**: システムは、消費者が商品詳細ページまたは商品一覧ページからカートに商品を追加できなければならない。

**.Quantity**: システムは、カート内の商品数量を変更（増減・削除）できなければならない。

**.Stock**: システムは、カートへの追加時に在庫数を確認し、在庫数を超える数量の追加を拒否しなければならない。（BR-EC-11 参照）

**Shop.Cart.Persist: カートの永続化**

**.Redis**: システムは、カートデータを Azure Cache for Redis に保存し、最後の操作から 30 日間保持しなければならない。（BR-EC-10 参照）

**.Login**: システムは、ゲストカートと CIAM ログイン済みカートを統合（マージ）する機能を提供しなければならない。ゲスト時にカートに追加した商品は、ログイン後もカートに引き継がれなければならない。

**.CrossDevice**: システムは、同一 CIAM アカウントのカートをデバイスをまたいで共有しなければならない。（Redis セッションキーを CIAM の consumer_id に紐付けることで実現）

---

### 3.4 Shop.Checkout: チェックアウト・Stripe 決済

**Shop.Checkout.Form: チェックアウトフォーム**

**.Address**: システムは、消費者が配送先住所（氏名・郵便番号・都道府県・市区町村・番地・建物名）を入力できるフォームを提供しなければならない。CIAM ログイン済みの場合は過去の配送先を選択できなければならない。

**.Shipping**: システムは、テナントが設定した送料（固定送料または無料）を表示しなければならない。（BR-EC-30 参照）

**.Summary**: システムは、注文サマリー（商品・数量・小計・送料・合計）をチェックアウト画面に表示しなければならない。

**Shop.Checkout.Payment: Stripe 決済**

**.StockReserve**: システムは、チェックアウト処理開始時に在庫を仮確保しなければならない。決済が 10 分以内に完了しない場合は仮確保を解除しなければならない。（BR-EC-12 参照）

**.Stripe**: システムは、Stripe Elements を使用してクレジットカード情報を収集し、Stripe に直接送信しなければならない。カード番号はシステム内に保存してはならない。（BR-EC-13 参照）

**.PaymentIntent**: システムは、Stripe の Payment Intent API を使用して決済の**オーソリ（仮売上）のみ**を実行しなければならない。オーソリ成功後に在庫を確定し、注文を `pending` 状態で登録しなければならない。**決済の確定（キャプチャ）はバッチ処理が注文データを工場に送信した時点で実施する**。（BR-EC-24 参照）

**.FactoryOrderData**: システムは、オーソリ完了後（注文 `pending` 登録と同時に）、`factory_order_data` テーブルへ工場送信用データレコードを作成しなければならない。このレコードはバッチ処理が工場に送信するためのデータソースとなる。（BR-EC-22 参照）

**.CancellationCutoff**: システムは、注文登録時に `cancellation_cutoff_at`（キャンセル期限 = 注文日時 + テナント設定のキャンセル受付時間、デフォルト 60 分）を設定しなければならない。（BR-EC-23 参照）

**.Failed**: システムは、オーソリが失敗した場合に消費者に明確なエラーメッセージを表示し、在庫仮確保を解除し、カートの内容を維持しなければならない。

**Shop.Checkout.Confirm: 注文受付**

**.OrderNumber**: システムは、注文受付後（オーソリ完了時）に `{テナントスラッグ}-{YYYYMMDD}-{8桁連番}` 形式の注文番号を生成しなければならない。（BR-EC-14 参照）

**.Email**: システムは、注文受付後に消費者のメールアドレスへ注文受付メール（注文番号・商品・合計・配送先・キャンセル期限）を送信しなければならない。

**.MaxItems**: システムは、1 注文あたりの商品点数が 100 品目を超える注文を拒否しなければならない。（BR-EC-31 参照）

---

### 3.5 Shop.Order: 注文管理・注文履歴

**Shop.Order.History: 注文履歴**

**.List**: システムは、CIAM ログイン済みの消費者に注文履歴（注文番号・注文日・合計金額・ステータス）の一覧を表示しなければならない。

**.Detail**: システムは、注文詳細（注文明細・配送先・ステータス・決済情報）を表示しなければならない。

**Shop.Order.Cancel: 注文キャンセル**

**.Cancel**: システムは、注文ステータスが `pending` かつ現在日時が `cancellation_cutoff_at` よりも前であれば、消費者が注文をキャンセルできなければならない。注文ステータスが `locked` 以降の場合はキャンセルを拒否しなければならない。（BR-EC-15、BR-EC-23 参照）

**.Void**: システムは、キャンセル時に Stripe の PaymentIntent キャンセル（void）を実行し、オーソリを解除しなければならない。カード利用者への課金は発生してはならない。

**.StockRestore**: システムは、キャンセル時に確保していた在庫を元に戻さなければならない。

## 6. 制約と前提

- テナントごとに独立した CIAM を使用するため、消費者は他テナントの EC サイトに同じアカウントでアクセスできない（BR-EC-01）。
- カード番号は Stripe が管理する。システムは Payment Method ID のみを保持する（BR-EC-13）。
- 注文時点では Stripe オーソリのみを実行し、バッチが工場に送信した時点でキャプチャ（決済確定）する（BR-EC-24）。
- バッチ処理の対象は `locked` ステータスの注文。`cancellation_cutoff_at` 到達時に自動的に `locked` に遷移する（BR-EC-23）。
- 注文時に `factory_order_data` テーブルへ工場送信用データを作成する（BR-EC-22）。

## 7. データフロー（注文受付〜工場送信〜注文確定の例）

```
消費者
  │
  ▼
[1] カートで商品選択（Redis キャッシュ）
  │
  ▼
[2] チェックアウト画面（在庫仮確保 → テナント DB 更新）
  │
  ▼
[3] Stripe Elements でカード情報入力（ブラウザから Stripe へ直接）
  │
  ▼
[4] Stripe Payment Intent オーソリ（バックエンド → Stripe API）
    ※ キャプチャ（決済確定）はまだ行わない
  │
  ▼
[5] 注文受付（テナント DB: orders 挿入・在庫確定・status = pending）
    + factory_order_data レコード作成（工場送信用データ）
    + cancellation_cutoff_at 設定（注文日時 + テナント設定時間、デフォルト 60 分）
  │
  ▼
[6] 注文受付メール送信（注文番号・キャンセル期限を含む）
  │
  ▼
[7] キャンセル期限（cancellation_cutoff_at）到達
    → 注文ステータス pending → locked（キャンセル不可）
    → order-batch-queue に注文イベント投入（FR-020）
  │
  ▼
[8] バッチワーカーが locked 注文を集約・CSV 生成・工場に送信（FR-020/FR-021）
    → Stripe PaymentIntent キャプチャ（決済確定）
    → 注文ステータス locked → confirmed
  │
  ▼
[9] 工場が出荷完了 → Webhook 通知（FR-022）
    → 注文ステータス confirmed → shipped
    → 消費者に発送通知メール送信
```
