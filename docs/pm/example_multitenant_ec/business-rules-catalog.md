## 1. テナントプロビジョニング（Entra ID）

| ルール ID | ルール名 | 定義 | 根拠 | 影響機能 |
|---------|---------|------|------|---------|
| BR-MT-01 | テナント自動プロビジョニング完了時間 | システムは、テナント登録のメール確認完了後 20 分以内に、Entra ID テナント・CIAM 設定・管理サイト OIDC アプリ登録・PostgreSQL DB・Blob コンテナ・カスタムドメインを自動プロビジョニングしなければならない | SM-4 達成のため | FR-010 |
| BR-MT-02 | Entra ID テナント自動作成 | システムは、Microsoft Graph API を使用して各テナント専用の Entra ID テナントを自動作成しなければならない。手動作成を主フローとしてはならない | オンボーディング工数削減（BO-3） | FR-010 |
| BR-MT-03 | CIAM 自動設定 | システムは、EC サイト向けの Azure AD External Identities（CIAM）をテナントの Entra ID テナントに自動設定しなければならない。ソーシャルログイン（Google）は標準で有効にする | 消費者認証の即時利用 | FR-010, FR-001 |
| BR-MT-04 | プロビジョニング失敗時のロールバック | テナントプロビジョニング中にいずれかのステップが失敗した場合、システムは作成済みリソースをすべて削除し、テナント状態を `provisioning_failed` に設定し、プラットフォーム管理者にアラートを送信しなければならない | 中途半端なリソース残留防止 | FR-010 |
| BR-MT-05 | 1 テナント = 1 Entra ID テナント | 1 つのテナント（顧客企業）に対して、必ず 1 つの専用 Entra ID テナントを割り当てなければならない。共有 Entra ID テナントをテナント間で使用してはならない | セキュリティ要件 | FR-010, FR-011 |

## 2. テナント設定・スラッグ

| ルール ID | ルール名 | 定義 | 根拠 | 影響機能 |
|---------|---------|------|------|---------|
| BR-MT-10 | スラッグの一意性 | テナントスラッグ（例: `myshop`）は ShopHub SaaS プラットフォーム内で一意でなければならない。スラッグは英数字とハイフンのみ（3〜63 文字）を許可する | ルーティング衝突防止 | FR-010 |
| BR-MT-11 | スラッグ変更禁止 | テナントスラッグは一度設定したら変更できない。変更が必要な場合はテナントを再作成する | URL 変更による混乱防止 | FR-010 |
| BR-MT-12 | カスタムドメインの形式 | EC サイトのカスタムドメインは `shop.{顧客ドメイン}`、管理サイトは `admin.{顧客ドメイン}` の形式を推奨する。顧客が DNS の CNAME 設定を行い、Azure Front Door で証明書を自動発行する | テナント独立性 | FR-010 |
| BR-MT-13 | タイムゾーン設定 | テナントのデフォルトタイムゾーンは `Asia/Tokyo（JST）` とする。夜間バッチの実行基準時刻はテナントのタイムゾーンに依存せず、常に JST で統一する | バッチスケジュールの一貫性 | FR-010, FR-020 |

## 3. 認証・Entra ID テナント分離

| ルール ID | ルール名 | 定義 | 根拠 | 影響機能 |
|---------|---------|------|------|---------|
| BR-MT-20 | JWT 有効期限 | システムが発行する JWT のアクセストークン有効期限は 1 時間、リフレッシュトークン有効期限は 30 日とする | セキュリティポリシー | FR-011 |
| BR-MT-21 | テナントルーティング | システムは、リクエストのホスト名（カスタムドメインまたはスラッグ）からテナントを識別し、適切なテナントコンテキストでリクエストを処理しなければならない | テナント間データ漏洩防止 | FR-011 |
| BR-MT-22 | JWT iss クレーム検証 | システムは、すべての API リクエストで JWT の `iss`（発行者）クレームがリクエストテナントの Entra ID テナント ID と一致することを検証しなければならない。不一致の場合は 401 を返す | Entra ID テナント分離の核心 | FR-011 |
| BR-MT-23 | クロステナントアクセス禁止 | テナント A の認証済みユーザーは、API・DB・Blob ストレージいずれにおいてもテナント B のデータにアクセスできてはならない | セキュリティ要件 | FR-011 |
| BR-MT-24 | テナント管理者ロール | テナント管理者は、自テナントの Entra ID テナントで定義されたロール（`ShopHub.Admin`）を持つユーザーのみが担当できる | 権限管理 | FR-010, FR-011 |

## 4. 消費者認証（CIAM）

| ルール ID | ルール名 | 定義 | 根拠 | 影響機能 |
|---------|---------|------|------|---------|
| BR-EC-01 | 消費者認証の分離 | EC サイトの消費者は、テナント専用の Azure AD External Identities（CIAM）で認証されなければならない。テナント A の消費者アカウントはテナント B の EC サイトにはアクセスできない | テナント間消費者分離 | FR-001, FR-011 |

## 6. 注文キュー駆動バッチ処理

| ルール ID | ルール名 | 定義 | 根拠 | 影響機能 |
|---------|---------|------|------|---------|
| BR-BATCH-01 | バッチフラッシュポリシー | バッチワーカーは (tenant_id, factory_id) 単位の集約バッファが **1,000 件**（SizeFlush）に達した場合、または最初のメッセージ追加から **30 分**（TimeFlush）が経過した場合に、即座に CSV 生成・転送処理を開始しなければならない。どちらかの条件を満たした時点でフラッシュを発動する | 工場への継続的データ提供・納期保証（BO-4） | FR-020 |
| BR-BATCH-02 | テナントごとの独立ジョブ | バッチは Azure Batch を使用し、テナントごとに独立したジョブとして処理しなければならない。1 テナントのジョブ失敗が他テナントのキュー処理に影響してはならない | テナント間データ混入防止・可用性 | FR-020, FR-011 |
| BR-BATCH-03 | キュー投入から転送完了までの最大遅延 | 注文確定時のキュー投入から工場への CSV 転送完了までの時間は、最大遅延（TimeFlush 30 分 + バッチ処理 + 転送 30 分）を合わせて **90 分以内**を目標とする。遅延が継続する場合はプラットフォーム管理者にアラートを発報する | 工場の製造準備への迅速なデータ提供（BO-4） | FR-020 |
| BR-BATCH-04 | 自動リトライとデッドレターキュー対応 | バッチジョブ失敗時は指数バックオフで自動リトライを 3 回実施する。3 回失敗した場合は該当メッセージを Azure Service Bus のデッドレターキューに移動し、プラットフォーム管理者とテナント管理者にアラートメールを送信する。デッドレターキューからの手動再キューイングを可能にする | 可用性・運用性 | FR-020 |
| BR-BATCH-05 | バッチ実行ログの記録 | バッチ処理ごとに、テナント ID・対象日・バッチシーケンス番号・抽出件数・処理件数・エラー件数・フラッシュ理由（size_flush/time_flush/manual）・開始時刻・完了時刻・ステータスを `batch_logs` テーブルに記録しなければならない | 監査・トラブルシューティング | FR-020 |
| BR-BATCH-06 | バッチ対象プラン | キュー駆動バッチ処理（FR-020）および工場データ連携（FR-021）は Professional プラン以上のテナントのみが利用できる。Starter プランのテナントは注文イベントをキューに投入してはならない | 課金モデルとの整合 | FR-020, FR-021 |
| BR-BATCH-07 | バッチの手動再実行 | プラットフォーム管理者は、テナント ID・対象期間・工場 ID を指定して手動再実行できなければならない。対象注文を order-batch-queue に再投入し、冪等性チェックにより重複送信を防止する | 障害復旧・保守性 | FR-020 |
| BR-BATCH-08 | バッチデータの一時保存期間 | バッチで生成した一時 CSV ファイル（Azure Blob）は、工場への転送完了確認後 72 時間以内に削除する | ストレージコスト管理 | FR-020, FR-021 |
| BR-BATCH-09 | バッチ処理の冪等性 | 同一 `order_id` のメッセージが複数回 order-batch-queue に投入された場合でも、工場への CSV に同一注文データを重複して含めてはならない。Azure Service Bus の重複排除（Deduplication Window: 10 分）とバッチワーカーのステータスチェックで保証する | 再実行時・リトライ時のデータ整合性 | FR-020 |
| BR-BATCH-10 | キュー滞留アラート | `order-batch-queue` のメッセージ滞留が **10,000 件**を超えた場合、Azure Monitor がプラットフォーム管理者に滞留アラートを送信しなければならない。Azure Batch Pool は自動スケールアウトして処理能力を増強する | 早期問題検知・SLA 維持 | FR-020 |

## 7. 工場データ連携

| ルール ID | ルール名 | 定義 | 根拠 | 影響機能 |
|---------|---------|------|------|---------|
| BR-FACTORY-01 | 工場ごとのフォーマット定義 | 工場ごとに異なる CSV フォーマット定義（列名・型・エンコーディング・区切り文字・ヘッダー有無・列順序）を工場マスタで管理しなければならない | 工場ごとの受入システムへの対応 | FR-021 |
| BR-FACTORY-02 | 転送方式の選択 | 工場ごとに SFTP 転送または Azure Blob 配置のいずれかを工場マスタで設定しなければならない | 工場システムの多様性への対応 | FR-021 |
| BR-FACTORY-03 | ファイル名規則 | 生成するファイル名は `{工場コード}_{テナントID}_{YYYYMMDD}_{連番2桁}.csv` の形式とする（例: `FACTORY-A_tenant-001_20261201_01.csv`）。連番は同一工場・同一日付のファイルが複数ある場合に使用する | ファイルの追跡可能性・誤配布検知 | FR-021 |
| BR-FACTORY-04 | 転送ログの記録 | ファイル転送ごとに、工場 ID・ファイル名・ファイルサイズ（バイト）・転送先・転送件数・ステータス（成功/失敗）・完了時刻を `transfer_logs` テーブルに記録しなければならない | 監査・納期保証の証明 | FR-021 |
| BR-FACTORY-05 | 転送失敗時のリトライ | ファイル転送が失敗した場合、指数バックオフ（1 分・2 分・4 分）で 3 回リトライする。3 回失敗した場合はプラットフォーム管理者とテナント管理者にアラートメールを送信する | BO-4 達成 | FR-021 |
| BR-FACTORY-06 | PGP 暗号化 | 工場マスタで `use_pgp = true` が設定されている場合、ファイルを工場の PGP 公開鍵で暗号化してから転送しなければならない。PGP 鍵は Azure Key Vault で管理する | 工場セキュリティ要件への対応 | FR-021 |
| BR-FACTORY-07 | SFTP 認証方式 | SFTP 接続は SSH キー認証のみを使用しなければならない。パスワード認証を使用してはならない。SSH 秘密鍵は Azure Key Vault に保存し、アプリケーションコードに含めてはならない | セキュリティポリシー | FR-021 |
| BR-FACTORY-08 | 転送完了通知 | ファイル転送が完了した場合、工場マスタの `notify_type` の設定に基づいて Webhook または メールで工場システムに転送完了を通知しなければならない。通知内容にはファイル名・件数・転送完了時刻を含める | 工場システムの処理トリガー | FR-021 |
| BR-FACTORY-09 | テナント間データ混入禁止 | 工場データ連携は、必ずテナント ID と工場マスタの `tenant_id` が一致する組み合わせでのみ実行しなければならない。テナント A の工場マスタに基づいて、テナント B のデータを転送してはならない | テナント間データ混入防止 | FR-021, FR-011 |
| BR-FACTORY-10 | 工場設定の変更管理 | フォーマット定義の変更は、次回バッチ実行日から適用される。変更の即時適用は手動再実行によって行う。変更履歴は監査ログに記録しなければならない | フォーマット変更の影響管理 | FR-021 |

## 7.2 工場出荷完了通知受信

| ルール ID | ルール名 | 定義 | 根拠 | 影響機能 |
|---------|---------|------|------|---------|
| BR-FACTORY-11 | 通知受信 URL の工場別一意性 | 出荷完了通知受信エンドポイントの URL は工場ごとに一意（`/api/v1/factories/{factory_id}/ship-notify`）とする。1 つの工場 ID に対して 1 つの URL のみ発行する | セキュリティ・追跡可能性 | FR-022 |
| BR-FACTORY-12 | HMAC-SHA256 署名認証の必須化 | 工場からの出荷完了通知はすべて HMAC-SHA256 署名（`X-ShopHub-Signature` ヘッダー）を含めなければならない。署名検証が失敗した場合は HTTP 401 を返し、注文ステータスを更新してはならない。HMAC キーは Azure Key Vault で管理し、平文でログに出力してはならない | 不正通知の拒否・セキュリティポリシー | FR-022 |
| BR-FACTORY-13 | テナント・工場の対応確認 | 出荷完了通知のペイロードの `tenant_id` は、エンドポイントの `factory_id` に紐づくテナントと一致しなければならない。不一致の場合は HTTP 403 を返し、クロステナント誤送信として Azure Monitor に記録する | テナント間データ混入防止 | FR-022, FR-011 |
| BR-FACTORY-14 | 出荷完了通知の冪等性 | 同一 `order_id` への出荷完了通知が複数回送信された場合、2 回目以降はスキップして HTTP 200 を返す。消費者への発送通知メールを重複して送信してはならない | 工場システムのリトライ対応・データ整合性 | FR-022 |
| BR-FACTORY-15 | 注文ステータス更新と消費者通知の必須化 | HMAC 検証・テナント確認が成功した出荷完了通知を受信した場合、必ず注文ステータスを `shipped` に更新し、かつ消費者に発送通知メールを送信しなければならない。注文ステータスの更新と消費者メール送信は不可分の処理とし、どちらか一方のみを行うことはできない（メール送信失敗時は注文更新を確定した上でリトライキューに投入する） | 消費者への迅速な発送情報提供 | FR-022, FR-001 |

## 9. テナントライフサイクル・データ保持

| ルール ID | ルール名 | 定義 | 根拠 | 影響機能 |
|---------|---------|------|------|---------|
| BR-MT-40 | 解約後データ保持期間 | テナントがサービスを解約した場合、テナントデータ（注文・商品・消費者情報・バッチログ・転送ログ）は解約後 90 日間保持する。テナント管理者は保持期間中にデータエクスポートできる | 顧客向けデータポータビリティ・個人情報保護法 | FR-010 |
| BR-MT-41 | 物理削除 | 90 日経過後、テナントの PostgreSQL DB インスタンス・Blob コンテナ・Entra ID テナントを物理削除する。削除ログは監査証跡として 7 年間保持する | ストレージコスト管理・個人情報保護法 | FR-010 |
| BR-MT-42 | バッチログ・転送ログ・通知ログの保持 | バッチ実行ログ・工場転送ログ・出荷完了通知受信ログは 2 年間保持する（テナント解約後も保持期間内は維持）。証拠能力を確保するため改ざんを防止する仕組みを設ける | 監査・コンプライアンス | FR-020, FR-021, FR-022 |
