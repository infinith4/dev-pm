## 1. 目的・スコープ

### 1.1 要件定義の目的

既存のシングルテナント版 TaskBoard を、Azure 上で提供するマルチテナント SaaS へ拡張するための要件定義を計画し、関係者の合意形成とレビュー順序を明確化する。要件定義の主要目的は、テナント間データ分離を前提にした Release 1 の対象範囲を確定し、事業目標（インフラコスト削減、ARR 拡大、オンボーディング工数削減）に対応する機能要件・非機能要件・業務ルール・トレーサビリティをベースライン化することである。

### 1.2 対象スコープ

| 区分 | 内容 |
|------|------|
| In Scope | マルチテナント SaaS 化のビジネス背景整理、Vision & Scope、SRS、機能要件、非機能要件、業務ルール、ユーザーストーリー、トレーサビリティ、Release 1 の優先度整理 |
| In Scope | テナント管理、テナントデータ分離、セルフサービスオンボーディング、課金・プラン管理、監査・セキュリティ・法務レビュー観点の整理 |
| Out of Scope | 詳細設計、実装、単体テスト、E2E テスト、インフラ構築手順の詳細化 |
| Out of Scope | Release 2 以降を前提とするカスタムドメイン、詳細利用量レポート、マルチリージョン対応、Terraform プロバイダー提供 |

## 6. リスク・前提条件

### 6.1 リスク

| リスク | 発生確率 | 影響 | 対策 |
|-------|---------|------|------|
| テナント分離の要件追加により設計・実装コストが増加する | 高 | 高 | セキュリティ部門レビューを要件定義中に前倒し実施し、分離方針を早期固定する |
| オンボーディング自動化の実現性不足で Release 1 スコープが不安定になる | 中 | 高 | Spike 結果を SRS と NFR に反映し、手動フォールバックを要件に明記する |
| Stripe / Azure AD など外部依存の仕様差分が判明する | 中 | 中 | 依存先 API の前提をレビューし、未確定事項を課題管理に残す |
| `traceability.md` が参照する UC-010 / UC-011 の個別文書が未作成で、追跡性にギャップが残る | 高 | 中 | ベースライン後の残課題として補完計画を登録し、設計開始前に解消する |
| 開発体制が 5 名固定であり、法務・セキュリティ指摘の増加に追従できない | 中 | 高 | Should 項目を Release 2 へ移送可能とし、Must を優先する |

### 6.2 前提条件

- Release 1 の目標日は 2026-03-31 で固定とする。
- テナント分離方式は Release 1 では Bridge モデル（DB-per-Tenant）を採用する。
- 認証基盤は Azure AD / SAML / OIDC を前提とし、独自認証フルスクラッチは対象外とする。
- 課金は Stripe を中心に検討し、Azure Marketplace 対応は Release 2 以降とする。
- 要件定義の主要成果物は `docs/requirements/multitenant/` 配下に集約する。
