## 1. Business Requirements

### 1.1 Background

自社開発の TaskBoard（シングルテナント版）は社内 20 チームで稼働し、月次アクティブユーザー 500 名・タスク件数 8 万件に達している。社外の取引先・パートナー企業 12 社から「同じシステムを使いたい」との要望が寄せられており、個別導入対応では保守コストが線形に増加している。現状の単一テナント構造では、顧客ごとに Azure サブスクリプションを分けてデプロイしているため、インフラ費用が顧客あたり月額 ¥80,000 かかっており、採算が取れる価格設定での SaaS 提供が困難である。

### 1.2 Business Opportunity

マルチテナント化により、アプリケーション層・監視基盤・CI/CD パイプラインを共有し、顧客あたりのインフラ費用を 1/4 以下に圧縮できる。外部企業向け SaaS として月額サブスクリプション課金モデルを採用することで、3 年以内に ARR ¥1.2 億を目指す。また、テナント単位の利用データが蓄積されることで、機能開発の優先度判断に使えるプロダクト分析基盤も整備できる。

### 1.5 Vision Statement

> **For** SaaS としてプロジェクト管理ツールを導入したい企業（5〜500名規模）
> **Who** 既製品では機能が過剰または不足し、自社運用サーバーの維持コストも避けたいと考えている
> **The** TaskBoard SaaS
> **Is a** Azure 上で動作するマルチテナント型プロジェクトタスク管理 SaaS
> **That** テナントごとにデータを完全に隔離しつつ、セルフサービスでオンボーディングからユーザー管理・課金まで完結する
> **Unlike** Jira / Asana などの高機能ツールや、自社サーバーへの個別インストール型製品
> **Our product** テナント単位のカスタマイズ（ドメイン・ブランディング・機能フラグ）を維持しながら、マルチテナント基盤によって低コストで継続的に機能追加を提供し続けることができる

### 1.6 Business Risks

| リスクID | リスク | 確率 | 影響度 | 軽減策 |
|---------|-------|------|-------|-------|
| RI-1 | テナント間データ漏洩が発生し信頼を失う | 0.2 | 9 | テナント分離アーキテクチャの設計レビュー・ペネトレーションテスト実施・RLS/テナントDB分離の多層防御 |
| RI-2 | 一部テナントの高負荷が他テナントに影響する（Noisy Neighbor） | 0.5 | 6 | テナントごとのリソース使用量クォータ設定・Azure API Management でのレート制限・プランごとの専用リソース割り当て |
| RI-3 | テナントオンボーディング自動化の障害でリリースが遅延する | 0.4 | 6 | Spike によるプロビジョニング自動化の事前検証・手動フォールバックフローの準備 |
| RI-4 | 競合 SaaS の価格攻勢により顧客獲得が困難になる | 0.3 | 6 | 差別化機能（カスタムドメイン・API 連携・日本語サポート）の早期投入 |
| RI-5 | 個人情報保護法・GDPR 対応が不十分で法的リスクが生じる | 0.2 | 9 | 法務レビューをリリース前に完了・データ居住地（リージョン）選択オプションを提供 |

### 1.7 Business Assumptions and Dependencies

#### Assumptions

| ID | 前提条件 | 誤りだった場合の影響 |
|----|---------|----------------|
| AS-1 | テナントは Azure AD または独自 IdP（SAML/OIDC）を保有している | 独自認証基盤の構築が必要となりスコープが拡大する |
| AS-2 | 顧客企業は月次サブスクリプション課金モデルを受け入れる | 一時払いや年払い対応の追加実装が必要になる |
| AS-3 | テナントあたりのユーザー数は最大 1,000 名を上限として設計する | 大規模テナント向けのスケーリング設計が必要になる |

#### Dependencies

| ID | 依存先 | 説明 | 影響範囲 |
|----|-------|------|---------|
| DE-1 | Azure Active Directory / Azure AD B2C | マルチテナント SSO および B2C 認証に使用する | テナント認証全般 |
| DE-2 | Stripe / Azure Marketplace | サブスクリプション課金・請求書発行 | 課金機能 |
| DE-3 | Azure Database for PostgreSQL Flexible Server | テナントごとのデータベース分離に使用する | データ分離全般 |
| DE-4 | Azure API Management | テナントルーティング・レート制限・API キー管理 | API ゲートウェイ |

## 2. Scope and Limitations

### 2.1 Major Features

| 機能ID | 機能名 | 説明 | 優先度 |
|-------|-------|------|-------|
| FE-1 | テナント管理 | テナントの作成・設定・停止・削除、プラン管理 | Must |
| FE-2 | テナントデータ分離 | テナントごとの PostgreSQL データベース分離（Bridge モデル） | Must |
| FE-3 | テナント認証・SSO | Azure AD / SAML 2.0 / OIDC によるテナント別 SSO 対応 | Must |
| FE-4 | セルフサービスオンボーディング | テナント登録からユーザー招待までをセルフで完結 | Must |
| FE-5 | サブスクリプション・課金管理 | プラン選択・クレジットカード決済・請求書発行 | Must |
| FE-6 | テナント別カスタムドメイン | `{tenant}.taskboard.jp` 形式のカスタムドメイン対応 | Should |
| FE-7 | 機能フラグ（テナント別） | プランに応じた機能の有効化・無効化 | Should |
| FE-8 | テナント別監視・利用量レポート | テナント管理者向けの利用状況ダッシュボード | Could |
| FE-9 | データエクスポート・ポータビリティ | テナントデータの CSV/JSON エクスポート、解約時のデータ返却 | Should |
| FE-10 | マルチリージョン対応 | データ居住地（Japan East / Japan West）の選択 | Won't（Release 1） |

### 2.2 Scope of Initial and Subsequent Releases

| 機能 | Release 1 | Release 2 | Release 3 |
|-----|----------|----------|----------|
| FE-1 テナント管理 | 作成・基本設定・停止 | プラン変更・詳細設定 | テナント階層（親子） |
| FE-2 データ分離 | DB-per-Tenant（Bridge モデル） | スキーマ分離オプション | Pool モデル（廉価プラン向け） |
| FE-3 テナント認証 | メール+パスワード・Azure AD SSO | SAML 2.0 対応 | OIDC カスタム IdP |
| FE-4 オンボーディング | セルフサービス（Web フォーム） | API によるプロビジョニング | Terraform プロバイダー |
| FE-5 課金 | Stripe 決済・月次請求書 | Azure Marketplace 対応 | 従量課金プラン |
| FE-6 カスタムドメイン | 未実装 | 実装 | ワイルドカード証明書自動更新 |
| FE-7 機能フラグ | 実装（プラン別） | テナント管理者が設定可能 | A/B テスト対応 |
| FE-8 利用量レポート | 未実装 | 基本ダッシュボード | 詳細分析・アラート |
| FE-9 データエクスポート | CSV エクスポートのみ | JSON + API | 自動スケジュールエクスポート |
| FE-10 マルチリージョン | 未実装 | 未実装 | 実装 |

### 2.3 Limitations and Exclusions

| ID | 対象外事項 | 対象外の理由 |
|----|---------|-----------|
| LI-1 | オンプレミス・プライベートクラウドへのインストール | SaaS 専用設計のため対応しない |
| LI-2 | テナント間のデータ共有・コラボレーション機能 | データ分離方針と相反するため将来の別プロダクトで検討 |
| LI-3 | Release 1 でのマルチリージョン（データ居住地）対応 | インフラ複雑度が高く Release 3 で対応 |

### 3.3 Deployment Considerations

- **移行戦略**: 既存シングルテナントのデータを移行するマイグレーションスクリプトを提供。既存ユーザーを最初のテナントとして移行する。
- **データ移行**: テナントごとに PostgreSQL データベースを新規作成し、既存データを一括インポート。
- **トレーニング**: テナント管理者向けオンボーディングガイド（Web）・30 分セットアップ動画を提供。エンドユーザー向けの操作変更はほぼない。
- **ロールアウト**: 社内テナント（Week 1）→ 既存取引先テナント（Week 3〜6）→ 一般公開（Week 8）。
