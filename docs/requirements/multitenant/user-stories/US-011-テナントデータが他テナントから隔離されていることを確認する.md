## ユーザーストーリー

> **As a** テナント管理者（顧客企業の IT 担当者）
> **I want to** 自社のデータが他の顧客企業からアクセスできないことを保証してほしい
> **So that** セキュリティポリシーおよびコンプライアンス要件を満たした上で SaaS を利用できるようにしたい

## 受入基準

### AC-001: テナント A のユーザーはテナント B の API にアクセスできない

```gherkin
Given テナント A のユーザーが有効な JWT（tenant_id = "tenant-a"）を保有している
When  テナント B のサブドメイン（https://tenant-b.taskboard.jp/api/tasks）に JWT を使ってリクエストを送信する
Then  HTTP 403 が返却される
  And レスポンスボディにテナント B のデータが含まれない
  And アクセス試行が Azure Monitor のセキュリティログに記録される
```

### AC-002: テナント A の JWT でテナント B のデータは取得できない

```gherkin
Given テナント A のユーザーが有効な JWT を保有している
  And テナント A の API エンドポイントにリクエストを送信する
When  レスポンスを確認する
Then  レスポンスに含まれるすべてのデータが tenant_id = "tenant-a" に属する
  And テナント B のデータ（プロジェクト・タスク・ユーザー等）は一切含まれない
```

### AC-003: テナント B の Blob Storage コンテナには直接アクセスできない

```gherkin
Given テナント A のユーザーがテナント B の Blob Storage コンテナ名（tenant-{tenant-b-id}）を知っている
When  Azure Blob Storage に直接アクセスを試みる
Then  HTTP 403 または 404 が返却される
  And テナント B のファイルにアクセスできない
```

### AC-004: テナント ID の改ざんを試みてもアクセスできない

```gherkin
Given 攻撃者がテナント A の有効な JWT を保有している
When  JWT の tenant_id クレームを "tenant-b" に書き換えてリクエストを送信する
Then  JWT 署名検証が失敗し HTTP 401 が返却される
  And テナント B のデータへのアクセスはできない
```

### AC-005: レート制限がテナントごとに独立して機能する

```gherkin
Given テナント A が Starter プラン（100 req/分 上限）を利用している
  And テナント B が Professional プラン（500 req/分 上限）を利用している
When  テナント A が 1 分間に 101 件のリクエストを送信する
Then  テナント A の 101 件目のリクエストが HTTP 429 で拒否される
  And テナント B への影響はなく、テナント B は引き続き 500 req/分 で API を利用できる
```

### AC-006: テナント分離違反が検出されるとアラートが発報される

```gherkin
Given JWT の tenant_id と API Gateway の X-Tenant-ID ヘッダーが一致しない不正リクエストが発生した
When  FastAPI ミドルウェアが不一致を検出する
Then  HTTP 403 が返却される
  And Azure Monitor にセキュリティインシデントレベルのログが記録される
  And プラットフォーム管理者に 5 分以内にアラートが届く
```

## 補足・制約

- テナント分離はペネトレーションテスト（外部業者）でリリース前に検証する（NFR-SEC-01）。
- 多層防御（Azure API Management → ミドルウェア → DB 接続 → ストレージ SAS）により、単一レイヤーの脆弱性でデータ漏洩が起きないこと。
- 参照: [FR-011 テナントデータ分離](../functional/FR-011-テナントデータ分離.md)、[NFR セキュリティ](../non-functional/NFR.md)
