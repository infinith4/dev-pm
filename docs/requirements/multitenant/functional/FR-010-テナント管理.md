### 概要

プラットフォーム管理者（SaaS 事業者側）およびテナント管理者（顧客企業側）が、テナントのライフサイクル全体（登録・設定・プラン変更・停止・削除）を管理する機能。テナント登録時には Azure リソース（PostgreSQL DB・Blob コンテナ・API キー）の自動プロビジョニングを行う。

---

### 機能要件

---

**Tenant.Provision: テナントの自動プロビジョニング**

**.Create**: システムは、テナント登録完了（メール確認）後、Platform DB にテナントレコードを作成しなければならない。テナントID は UUID v4 で採番する。

**.DB**: システムは、テナントごとに専用の Azure Database for PostgreSQL Flexible Server インスタンスまたはデータベースを作成しなければならない。接続文字列はプレーンテキストで保存してはならない。（BR-MT-01 参照）

**.Schema**: システムは、テナント DB に最新スキーマを自動適用（マイグレーション実行）しなければならない。

**.Storage**: システムは、テナントごとに Azure Blob Storage コンテナを作成しなければならない（命名規則: `tenant-{tenant_id}`）。

**.KeyVault**: システムは、テナント DB 接続文字列・ストレージキー・API キーを Azure Key Vault に登録し、Platform DB には Key Vault 参照 URI のみを保存しなければならない。（BR-MT-02 参照）

**.Time**: システムは、メール確認完了から 3 分以内にプロビジョニングを完了しなければならない。（BO-3、BR-MT-03 参照）

**.Status**: プロビジョニング中はテナントステータスを `provisioning` とし、完了後に `trial` に更新しなければならない。

**.Notify**: プロビジョニング完了後、システムはテナント管理者にオンボーディング完了メール（ログイン URL・管理者ガイドリンク含む）を送信しなければならない。

**.Failure**: プロビジョニングのいずれかのステップが失敗した場合、システムはロールバック（作成済みリソースを削除）し、テナントステータスを `provisioning_failed` に設定し、プラットフォーム管理者にアラートを送信しなければならない。

---

**Tenant.Config: テナント設定の管理**

**.Subdomain**: テナント管理者は、サインアップ時に設定したサブドメイン（`{subdomain}.taskboard.jp`）を確認できなければならない。サブドメインは作成後に変更できない。（BR-MT-10 参照）

**.Name**: テナント管理者は、テナントの表示名を変更できなければならない。

**.SSO**: テナント管理者は、Azure AD アプリ登録情報（テナントID・クライアントID・クライアントシークレット）を設定し、SSO を有効化・無効化できなければならない。

**.SSOTest**: テナント管理者は、SSO 設定を保存する前に接続テストを実行し、結果を確認できなければならない。

**.FeatureFlag**: プラットフォーム管理者は、テナントごとに機能フラグ（ダッシュボード・API 連携・カスタムドメイン等）を有効化・無効化できなければならない。（BR-MT-11 参照）

**.Timezone**: テナント管理者は、テナントのタイムゾーン（デフォルト: Asia/Tokyo）を設定できなければならない。

**.Logo**: テナント管理者は、テナントのロゴ画像（PNG/SVG、最大 512KB）をアップロードできなければならない。（Release 2 以降）[TBD-010-01: ロゴ表示の対象画面の確定, PM, 2026-02-28]

---

**Tenant.Lifecycle: テナントライフサイクル管理**

**.Suspend**: プラットフォーム管理者は、規約違反・未払い等の理由でテナントを一時停止（`suspended`）できなければならない。停止中のテナントユーザーはログイン時にエラーメッセージを受け取る。

**.Resume**: プラットフォーム管理者は、停止したテナントを再開（`active`）できなければならない。

**.Cancel**: テナント管理者は、解約を申請できなければならない。解約後 90 日間はデータが保持され、その後物理削除される。（BR-MT-40 参照）

**.Delete**: プラットフォーム管理者は、解約から 90 日経過後にテナントの全リソース（DB・ストレージ・Key Vault シークレット）を物理削除できなければならない。削除操作は監査ログに記録されなければならない。

**.Export**: テナント管理者は、解約申請前にテナントデータ（プロジェクト・タスク・ユーザー・活動ログ）を JSON 形式でエクスポートできなければならない。（FE-9 参照）

---

**Tenant.UserManagement: テナント内ユーザー管理**

**.Invite**: テナント管理者は、メールアドレスとロールを指定してユーザーを招待できなければならない。

**.RoleAssign**: テナント管理者は、テナントメンバーのロール（テナント管理者 / PM / 開発者 / 閲覧者）を変更できなければならない。

**.Remove**: テナント管理者は、テナントメンバーをテナントから削除できなければならない。削除されたユーザーのデータ（タスク作成履歴・コメント）は保持する。

**.MaxUsers**: システムは、テナントのアクティブユーザー数がプランの上限に達した場合、新規招待を拒否し、テナント管理者に警告を表示しなければならない。（BR-MT-12 参照）

---

### 入力・出力

#### テナント登録時の入力

| フィールド | 型 | 必須 | 制約 | 説明 |
|----------|----|----|------|------|
| company_name | string | ✓ | max 200文字 | テナント（企業）表示名 |
| subdomain | string | ✓ | 3〜63文字、英数字・ハイフン、先頭は英字（BR-MT-10） | サブドメイン |
| admin_email | string | ✓ | RFC 5321 準拠、max 254文字 | 管理者メールアドレス |
| admin_password | string | ✓ | min 12文字、英大文字・小文字・数字・記号を各1文字以上含む（BR-MT-20） | 管理者パスワード |
| plan_id | string | ✓ | Starter / Professional / Enterprise | 選択プラン |

#### テナント情報の出力

| フィールド | 型 | 説明 |
|----------|----|----|
| tenant_id | UUID | テナント一意識別子 |
| subdomain | string | サブドメイン |
| status | enum | active / trial / suspended / provisioning / provisioning_failed / cancelled |
| plan | object | { id, name, max_users, max_projects } |
| trial_ends_at | datetime | トライアル終了日時（トライアル中のみ） |
| created_at | datetime | テナント作成日時（UTC） |

| BR-MT-40 | Tenant.Lifecycle.Cancel | 解約後 90 日間データを保持し、90 日経過後に自動物理削除する。削除の 7 日前に管理者にリマインドメールを送信する |

---

### 例外・エラー処理

| ケース | 条件 | システムの応答 |
|-------|------|-------------|
| サブドメイン重複 | 入力されたサブドメインが既に使用中 | 「このサブドメインは使用できません」と表示し、代替案を提示する |
| プロビジョニング失敗 | DB 作成または Key Vault 登録が失敗した | 作成済みリソースをロールバックし、プラットフォーム管理者に PagerDuty 経由でアラートを発報する |
| プラン上限超過 | ユーザー数がプラン上限に達した状態で招待しようとした | 「ユーザー数の上限（X名）に達しています。プランをアップグレードしてください」と表示する |
