## 1. Business Requirements

### 1.1 Background

中小〜中規模の小売事業者（BtoC）向けに EC サイトおよびバックオフィス管理サイトを個別構築・保守してきたが、顧客数の増加に伴いコストと納期が問題となっている。現状では顧客ごとに Azure サブスクリプションを分離してデプロイしており、インフラ費用が顧客あたり月額 ¥120,000 かかっている。また、顧客ごとに認証基盤（Azure Entra ID テナント）を手動でプロビジョニングするのに 16 人時を要しており、オンボーディングのボトルネックになっている。

さらに、各 EC 事業者は毎日大量の注文データを自社が契約する製造工場に送付しなければならない。現状では各社が個別に夜間バッチスクリプトを作成・保守しており、工場ごとに異なる CSV フォーマットへの対応や SFTP/Azure Blob 転送の管理が属人化している。夜間バッチの障害や工場へのデータ未着が翌日の製造遅延につながるリスクが高まっている。

EC サイト（消費者向け）と管理サイト（店舗スタッフ向け）の両方を、顧客ごとに専用の Azure Entra ID テナントを割り当てた上で提供するとともに、日次 1,000 万件規模（全テナント合計）の注文データをキュー駆動バッチで並列処理し、工場ごとに定められた CSV フォーマットで自動配布する SaaS プラットフォームを構築する。これにより、データ・認証の完全分離と低コスト運用、および工場へのデータ納期遵守を同時に実現する。

### 1.2 Business Opportunity

マルチテナントアーキテクチャにより、アプリケーション層・CI/CD・監視基盤を共有しながら、各顧客の Entra ID テナント・データベース・ストレージを分離できる。夜間バッチ基盤（Azure Batch）を共有することで、テナントごとの個別バッチ実装コストをなくし、工場フォーマット定義をマスタ管理することでフォーマット変更への対応工数を大幅削減できる。顧客の店舗スタッフは自社の Entra ID アカウントで管理サイトへ SSO でき、消費者は顧客テナントの Azure AD External Identities（CIAM）で認証される。

### 1.5 Vision Statement

> **For** EC サイトと管理サイトを低コストかつ安全に運営し、工場への注文データ自動連携を求める中小規模の小売事業者
> **Who** 自社開発・個別インストール型の EC システムでは保守負担が大きく、夜間バッチの属人化・工場フォーマット対応コストに悩んでいる
> **The** ShopHub SaaS
> **Is a** Azure 上で動作するマルチテナント型 EC + 管理サイト + 工場データ連携 SaaS プラットフォーム
> **That** 顧客ごとに専用の Azure Entra ID テナントを自動プロビジョニングし、EC サイト・管理サイトを完全なデータ・認証分離の下で提供するとともに、日次 1,000 万件規模（全テナント合計）の注文データをキュー駆動バッチで並列処理し、工場ごとの CSV フォーマットで自動配布する
> **Unlike** 共有 IdP 型のマルチテナント SaaS や、夜間バッチを含まないオンプレミス型の EC パッケージ
> **Our product** Entra ID テナント分離により最高水準のセキュリティを維持しながら、EC サイト・管理サイト・夜間バッチ・工場データ連携をワンストップで提供できる

### 1.6 Business Risks

| リスクID | リスク | 確率 | 影響度 | 軽減策 |
|---------|-------|------|-------|-------|
| RI-1 | テナント間データ漏洩が発生し信頼・コンプライアンスを失う | 0.1 | 10 | Entra ID テナント単位分離・テナント別 DB・ペネトレーションテスト・多層防御 |
| RI-2 | Entra ID テナントの自動プロビジョニング失敗でオンボーディングが遅延する | 0.4 | 7 | Microsoft Graph API の Spike 検証・手動フォールバックフロー準備 |
| RI-3 | 夜間バッチが 04:00 JST までに完了せず翌日の工場製造が遅延する | 0.3 | 9 | Azure Batch ノード数の動的スケール・タイムアウト監視・アラート即時通知 |
| RI-4 | 工場ごとの CSV フォーマット定義の変更管理が困難になる | 0.5 | 6 | フォーマット定義をデータベースで管理し、管理画面から変更可能にする |
| RI-5 | 一部テナントの高トラフィックが他テナントに影響する（Noisy Neighbor） | 0.4 | 6 | テナント別リソースクォータ・Azure Front Door でのレート制限 |
| RI-6 | 個人情報保護法・特定商取引法対応が不十分で法的リスクが生じる | 0.2 | 9 | 法務レビューをリリース前に完了・特定商取引法表示テンプレートの提供 |
| RI-7 | SFTP/Blob 転送失敗により工場が注文データを受け取れない | 0.3 | 8 | 3 回自動リトライ・失敗時即時アラート・手動再転送機能の提供 |

### 1.7 Business Assumptions and Dependencies

#### Assumptions

| ID | 前提条件 | 誤りだった場合の影響 |
|----|---------|----------------|
| AS-1 | 顧客（テナント）は Entra ID テナントの管理権限を SaaS プラットフォームに委任できる | Microsoft Graph API 経由での自動テナント作成が不可となりスコープが拡大する |
| AS-2 | 消費者向け認証は Azure AD External Identities（CIAM）で実現できる | 別途 Auth0 等の CIAM サービスを導入する必要が生じる |
| AS-3 | テナントあたりの日次注文数は最大 100 万件、全テナント合計で日次 1,000 万件を上限として設計する | スケーリング設計の見直しが必要になる |
| AS-4 | 顧客は月次サブスクリプション課金モデルを受け入れる | 年払い・従量課金対応の追加実装が必要になる |
| AS-5 | 工場は SFTP サーバーまたは Azure Blob へのアクセス環境を保有している | 別途工場側のシステム整備が必要になる |
| AS-6 | 工場ごとの CSV フォーマット定義はテナント管理者が管理画面で登録・更新できる | フォーマット変更のたびにプラットフォーム管理者の対応が必要になる |

### 2.3 Limitations and Exclusions

| ID | 対象外事項 | 対象外の理由 |
|----|---------|-----------|

### 3.3 Deployment Considerations

- **移行戦略**: 既存個別 EC サイトのデータを移行するマイグレーションスクリプトを提供。既存顧客を最初のテナントとして移行する。
- **データ移行**: テナントごとに PostgreSQL データベースと Entra ID テナントを新規作成し、既存データを一括インポート。工場フォーマット定義も初期データとして投入する。
- **トレーニング**: テナント管理者向けオンボーディングガイド（Web）・工場設定動画・バッチ監視画面マニュアルを提供。
- **ロールアウト**: 社内検証テナント（Week 1〜2）→ 既存顧客テナント（Week 4〜8、バッチ含む）→ 新規顧客向け一般公開（Week 10〜）。
