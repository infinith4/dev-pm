## ユーザーストーリー

**As a** ShopHub SaaS を利用するテナント管理者（情報セキュリティ部門のレビュアーも含む）

**I want to** テナント A のデータが技術的に他のテナント（テナント B 等）から完全に隔離されていることを確認したい

**So that** 顧客・消費者の個人情報・注文データ・工場データが他テナントに漏洩するリスクがないと確信でき、社内セキュリティ審査を通過できる

## 受入基準

### AC-001: Entra ID テナント分離（認証層）

**Given** テナント B の Entra ID テナントの認証情報（JWT）を持つ悪意のあるリクエスト

**When** テナント A の管理サイト API（`admin.myshop.jp/api/orders`）を呼び出す

**Then**
- JWT の `iss` クレームがテナント A の Entra ID テナント ID と一致しない（BR-MT-22）
- HTTP 401 Unauthorized が返される
- Azure Monitor にセキュリティアラートが記録される

### AC-002: テナント A の消費者アカウントでテナント B の EC サイトにアクセス不可

**Given** テナント A の CIAM で認証済みの消費者アカウント

**When** テナント B の EC サイト（`shop.othershop.jp`）にアクセスする

**Then**
- テナント B の CIAM での再認証を要求される
- テナント A の CIAM 認証情報はテナント B では無効（BR-EC-01）
- テナント B の商品・注文情報はまったく表示されない

### AC-003: API 層のテナントスコープ保証

**Given** テナント A の正規 JWT（iss クレームが一致）を持つリクエスト

**When** テナント B のリソースへのアクセス URL（`/api/tenants/{tenantB-id}/orders`）を直接指定する

**Then**
- HTTP 403 Forbidden が返される（BR-MT-23）
- テナント B の注文データは返されない
- テナント B のリソース URL へのアクセス試行が Azure Monitor のアクセスログに記録される

### AC-004: テナント別 PostgreSQL DB の物理分離

**Given** テナント A と テナント B がそれぞれ独立した PostgreSQL インスタンスを持つ

**When** テナント A のアプリケーションが DB に接続する

**Then**
- テナント A 専用の接続文字列（Azure Key Vault 管理）のみを使用する
- テナント B の DB インスタンスへの接続文字列はテナント A のアプリケーションからアクセスできない（FR-011）
- テナント A の DB へのクエリはすべてテナント A のデータのみを返す

### AC-005: Blob ストレージのテナント分離

**Given** テナント A の Blob コンテナ（`tenant-{tenantA-id}`）とテナント B の Blob コンテナ（`tenant-{tenantB-id}`）

**When** テナント A の SAS トークンを使ってテナント B のコンテナにアクセスしようとする

**Then**
- Azure Blob Storage によりアクセスが拒否される（403 Forbidden）
- テナント A の SAS トークンはテナント A のコンテナのみに有効（FR-011）

### AC-006: Azure Front Door WAF のレート制限

**Given** テナント A の EC サイトに対して過剰なリクエスト（1 分あたり 1,001 リクエスト以上）が発生

**When** テナント A からのリクエストが 1,001 件目を超える

**Then**
- Azure Front Door WAF がテナント A のリクエストのみを 429 Too Many Requests で制限する（BR-MT-50）
- テナント B へのリクエストは影響を受けない（Noisy Neighbor 防止）

### AC-007: テナント A のバッチ処理でテナント B の注文データが出力されない

**Given** テナント A（10,000 件の注文）とテナント B（5,000 件の注文）が同日に存在する

**When** 夜間バッチが実行され、テナント A のジョブが完了する

**Then**
- テナント A のバッチ出力 CSV ファイルに含まれる注文番号はすべてテナント A の注文番号（`myshop-XXXXXXXX`）である
- テナント B の注文番号（`othershop-XXXXXXXX`）はテナント A の CSV ファイルに含まれない（BR-BATCH-02, FR-011）
- テナント A のジョブとテナント B のジョブは独立した Azure Batch ノードで実行される
- テナント A のジョブがテナント B の DB に接続を試みた場合、Azure Key Vault のアクセスポリシーで拒否される

### AC-008: テナント A の工場データファイルにテナント B のデータが含まれない

**Given** テナント A が工場 `FACTORY-A` に、テナント B が工場 `FACTORY-B` に注文データを転送する設定

**When** 夜間バッチ後に工場データ連携が実行される

**Then**
- 工場 `FACTORY-A`（テナント A の工場）に転送されるファイルには、テナント A の注文データのみが含まれる
- 工場 `FACTORY-A` にテナント B の注文データが誤って含まれることはない（BR-FACTORY-09, FR-011）
- ファイル内の各行の「テナントID」列がテナント A の ID であることを自動検証テストで確認できる
- テナント A のファイルが誤って工場 `FACTORY-B`（テナント B の工場）に転送されることはない

## 技術メモ

- **JWT iss 検証**: ミドルウェアで `jwt.iss == tenant.entra_tenant_id` を全 API リクエストで検証（BR-MT-22）
- **バッチテナント分離**: 各 Azure Batch ジョブはジョブコンテキストの `tenant_id` のみの DB 接続文字列を Azure Key Vault から取得（BR-BATCH-02）
- **工場データ検証**: バッチ出力 CSV の自動検証テスト（ファイル内テナント ID = ジョブコンテキストの tenant_id を全行チェック）
