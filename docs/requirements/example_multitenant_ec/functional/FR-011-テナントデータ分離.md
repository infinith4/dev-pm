## 1. 概要

ShopHub SaaS のマルチテナントアーキテクチャにおいて、テナント間のデータ漏洩・混入を防止するための多層的なデータ分離機能を定義する。Entra ID テナント分離（認証層）、Azure Front Door ルーティング（ネットワーク層）、テナント別 PostgreSQL DB（データ層）、テナント別 Blob コンテナ（ストレージ層）、テナント別 Azure Batch ジョブ（バッチ層）を組み合わせて実現する。

**関連**:
- FE-2（テナントデータ分離）
- BR-MT-20〜BR-MT-24, BR-MT-50〜BR-MT-51
- UC-002（店舗スタッフが管理サイトへ Entra ID SSO でログインする）
- US-011（テナントデータが他テナントから隔離されていることを確認する）

## 2. 機能要件

### 2.1 Isolation.Identity: Entra ID テナント分離（認証層）

**Isolation.Identity.EntraID: Entra ID テナント単位の分離**

**.TenantPerCustomer**: システムは、1 テナント（顧客企業）に対して 1 つの専用 Entra ID テナントを割り当てなければならない。複数テナントが同一 Entra ID テナントを共有してはならない。（BR-MT-05 参照）

**.JwtIssValidation**: システムは、すべての API リクエストで JWT の `iss`（発行者）クレームをリクエストテナントの Entra ID テナント ID と照合し、不一致の場合は HTTP 401 を返さなければならない。（BR-MT-22 参照）

**.CIAM**: システムは、EC サイトの消費者認証にテナント専用の Azure AD External Identities（CIAM）を使用し、テナント A の消費者アカウントがテナント B の EC サイトにアクセスできないことを保証しなければならない。（BR-EC-01 参照）

**Isolation.Identity.Session: セッション分離**

**.SessionToken**: システムは、JWT アクセストークン（有効期限 1 時間）とリフレッシュトークン（有効期限 30 日）を発行しなければならない。（BR-MT-20 参照）

**.IsolatedSession**: システムは、セッションが他テナントのリソースにアクセスできないことを保証しなければならない。セッションにはテナント ID を含め、すべての API リクエストでセッションのテナント ID と URL パスのテナント ID が一致することを検証しなければならない。

---

### 2.2 Isolation.Routing: Azure Front Door + WAF によるテナントルーティング

**Isolation.Routing.FrontDoor: Front Door ルーティング**

**.HostRouting**: システムは、Azure Front Door でリクエストのホスト名（カスタムドメインまたは `{スラッグ}.shophub.jp`）からテナントを識別し、適切なバックエンドにルーティングしなければならない。（BR-MT-21 参照）

**.WAF**: システムは、Azure Front Door の WAF（Web Application Firewall）でテナントごとにレート制限（1 分あたり最大 1,000 リクエスト）を適用し、超過した場合は 429 Too Many Requests を返しなければならない。（BR-MT-50 参照）

**.TenantHeader**: システムは、Front Door からバックエンドへのリクエストに `X-Tenant-ID` ヘッダーを付与し、バックエンドで検証しなければならない。

---

### 2.3 Isolation.Database: テナント別 PostgreSQL DB（Bridge モデル）

**Isolation.Database.Separate: DB 物理分離**

**.SeparateDB**: システムは、テナントごとに独立した Azure Database for PostgreSQL Flexible Server インスタンスを使用しなければならない（Bridge モデル）。テナント間で DB インスタンスを共有してはならない。

**.ConnectionString**: システムは、テナントの DB 接続文字列を Azure Key Vault で管理し、アプリケーションコード・ログには出力しないようにしなければならない。

**Isolation.Database.AppValidation: アプリ層でのテナント検証**

**.TenantCheck**: システムは、テナント DB への接続前に、Platform DB のテナントレコードとリクエストのテナント ID が一致することを検証しなければならない。

**.NoDirectAccess**: テナント DB への直接 SQL アクセス（アプリ API を経由しないアクセス）は、バッチ専用接続文字列を使用する Azure Batch ジョブを除いて禁止しなければならない。（BR-MT-51 参照）

---

### 2.4 Isolation.Storage: テナント別 Blob コンテナ

**Isolation.Storage.Container: Blob コンテナ分離**

**.SeparateContainer**: システムは、テナントごとに独立した Azure Blob Storage コンテナ（`tenant-{tenant_id}`）を使用しなければならない。テナント間でコンテナを共有してはならない。

**.SASToken**: システムは、テナントの Blob コンテナへのアクセスにSAS（Shared Access Signature）トークンを使用し、SAS トークンは有効期限を 1 時間以下に設定しなければならない。

**.BatchIntermediate**: 夜間バッチで生成した一時 CSV ファイルは、テナント専用の Blob コンテナ内の `batch/{YYYYMMDD}/` 配下に保存しなければならない。他テナントのバッチが同一コンテナにアクセスできないことを保証しなければならない。

---

### 2.5 Isolation.Batch: バッチ処理のテナント分離

**Isolation.Batch.Job: Azure Batch ジョブ分離**

**.SeparateJob**: システムは、夜間バッチ処理をテナントごとに独立した Azure Batch ジョブとして実行しなければならない。1 つのジョブが複数テナントのデータを処理してはならない。（BR-BATCH-02 参照）

**.TenantContext**: 各 Azure Batch ジョブは、起動時にテナント ID をコンテキストとして受け取り、すべてのデータ操作（DB 接続・Blob アクセス・工場データ生成）でテナント ID を検証しなければならない。

**.IsolatedOutput**: システムは、テナント A のバッチジョブがテナント B の注文データを出力できないことを保証しなければならない。（BR-BATCH-02, BR-FACTORY-09 参照）

**Isolation.Batch.Queue: キュー分離**

**.TenantQueue**: システムは、Azure Service Bus でテナントごとのジョブメッセージを管理し、テナント A のジョブメッセージがテナント B のジョブを誤って起動しないことを保証しなければならない。

**.JobId**: 各バッチジョブには `{tenant_id}-{YYYYMMDD}-{uuid}` 形式のジョブ ID を付与し、ログの追跡可能性を確保しなければならない。

---

### 2.6 Isolation.API: API 層でのテナントスコープ保証

**Isolation.API.Middleware: テナントコンテキスト検証ミドルウェア**

**.Middleware**: システムは、すべての API エンドポイントにテナントコンテキスト検証ミドルウェアを適用しなければならない。ミドルウェアは JWT の `iss` クレームとリクエスト URL のテナント識別子を照合する。（BR-MT-22 参照）

**.ResourceScope**: システムは、API レスポンスにテナントの範囲外のデータを含めてはならない。データ取得クエリには常にテナント ID の WHERE 条件を適用しなければならない。

**.403**: テナント外リソースへのアクセス試行に対して HTTP 403 Forbidden を返さなければならない。

---

### 2.7 Isolation.Audit: 監査ログ

**Isolation.Audit.Log: 監査ログの記録**

**.LoginLog**: システムは、管理サイトへの Entra ID SSO ログイン・ログアウトを Azure Monitor に記録しなければならない（テナント ID・ユーザー ID・ログイン時刻・IP アドレス）。

**.AccessLog**: システムは、テナント外リソースへのアクセス試行（403 エラー）を Azure Monitor にアラートとして記録しなければならない。

**.EntraSigninLog**: システムは、Entra ID サインインログ（成功・失敗・MFA 状況）を Azure Monitor に集約し、プラットフォーム管理者が参照できるようにしなければならない。

**.BatchAuditLog**: システムは、バッチジョブの実行ログ（テナント ID・ジョブ ID・実行日・処理件数・エラー件数・完了時刻）をテナント DB の `batch_logs` テーブルに記録しなければならない。（BR-BATCH-05 参照）

**.TransferAuditLog**: システムは、工場へのファイル転送ログ（工場 ID・ファイル名・件数・転送先・ステータス・完了時刻）を転送テーブルに記録しなければならない。（BR-FACTORY-04 参照）

## 3. 分離モデルの概要図

```
┌──────────────────────────────────────────────────────────────┐
│ テナント A                                                     │

│  │ Entra ID テナント│  │ PostgreSQL DB-A   │  │ Blob コンテナ│ │
│  │ CIAM（消費者）  │  │（注文・商品・消費者）│  │ tenant-A     │ │
│  │ OIDC アプリ    │  └──────────────────┘  └──────────────┘ │
│  │ JWT iss: A    │                                            │
│  └────────────────┘  ┌──────────────────┐                    │
│                       │ Azure Batch Job-A │（独立ジョブ）      │
│                       │（テナント A の    │                    │
│                       │ 注文のみ処理）    │                    │
│                       └──────────────────┘                    │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ テナント B                                                     │
│  ┌────────────────┐  ┌──────────────────┐  ┌──────────────┐ │
│  │ Entra ID テナント│  │ PostgreSQL DB-B   │  │ Blob コンテナ│ │
│  │ CIAM（消費者）  │  │（注文・商品・消費者）│  │ tenant-B     │ │
│  │ OIDC アプリ    │  └──────────────────┘  └──────────────┘ │
│  │ JWT iss: B    │                                            │
│  └────────────────┘  ┌──────────────────┐                    │
│                       │ Azure Batch Job-B │（独立ジョブ）      │
│                       │（テナント B の    │                    │
│                       │ 注文のみ処理）    │                    │
│                       └──────────────────┘                    │
└──────────────────────────────────────────────────────────────┘

共有レイヤー（アプリ基盤・Azure Front Door・Azure Batch Pool）
  ※ アプリ・バッチ基盤は共有、データ・認証・ジョブは分離
```

## 4. ペネトレーションテスト要件

テナント分離が正しく機能することを以下のシナリオでペネトレーションテストにより検証する:

| テストID | シナリオ | 期待結果 |
|---------|---------|---------|
| PT-001 | テナント A の JWT を使ってテナント B の API を呼び出す | HTTP 401（JWT iss 不一致） |
| PT-002 | テナント A の認証済みユーザーがテナント B のリソース URL を直接リクエスト | HTTP 403 |
| PT-003 | テナント A の CIAM アカウントでテナント B の EC サイトにアクセス | ログイン失敗（CIAM 分離） |
| PT-004 | テナント A のバッチジョブがテナント B の DB に接続を試みる | 接続拒否（DB 接続文字列が分離） |
| PT-005 | テナント A のバッチ出力 CSV にテナント B の注文データが含まれる | 含まれないことを件数・注文番号で確認 |
| PT-006 | テナント A の工場データファイルにテナント B のデータが混入する | 混入しないことを確認（BR-FACTORY-09） |
