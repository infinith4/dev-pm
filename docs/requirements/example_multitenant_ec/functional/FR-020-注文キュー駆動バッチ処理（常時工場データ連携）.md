## 1. 概要

注文が `locked`（キャンセル期限到達・工場送信待ち）ステータスに遷移した時点で Azure Service Bus キューに注文イベントを投入し、常時稼働するバッチワーカー（Azure Batch）がキューから注文を取得・集約して、`factory_order_data` テーブルに保持されている工場送信用データを CSV に変換し、工場データ連携（FR-021）に引き渡す。バッチが工場にデータを送信した後、Stripe PaymentIntent のキャプチャ（決済確定）を実行し、注文ステータスを `confirmed` に更新する。

**設計の核心**: 工場への送信タイミングは固定スケジュールではなく、キューに蓄積された注文量または経過時間（フラッシュ間隔）に基づいてバッチが随時生成される。注文時は Stripe オーソリのみで、決済確定は工場送信後に行う。

**処理規模**:
- 全テナント合計: 日次 1,000 万件
- テナントあたり: 最大 100 万件/日
- 想定テナント数: 最大 100 テナント（Professional/Enterprise）
- バッチフラッシュ間隔: 最大 30 分（設定可能）

**関連**:
- FE-6（工場データ連携バッチ）
- BR-BATCH-01〜BR-BATCH-10
- UC-003（注文キューから工場にデータを送信する）
- US-020（注文データを工場に継続的に送る）
- FR-021（工場データ連携）への引き渡し
- FR-001（EC サイト）─ 注文確定イベントの発行元
- FR-011（Isolation.Batch: バッチ処理のテナント分離）

## 2. 機能要件

### 2.1 Batch.Enqueue: 注文確定時のキュー投入

**Batch.Enqueue.Trigger: 注文イベントの発行**

**.OnLocked**: システムは、注文ステータスが `locked`（キャンセル期限到達）に遷移した時点で、当該注文の注文イベントメッセージを Azure Service Bus の注文キュー（`order-batch-queue`）に投入しなければならない。`locked` 遷移はバッチスケジューラーが `cancellation_cutoff_at` を過ぎた `pending` 注文を定期チェック（1 分ごと）して自動実行する。（BR-EC-23、BR-BATCH-01 参照）

**.MessageSchema**: キューに投入するメッセージには以下を含めなければならない:

```json
{
  "event_id": "UUID",
  "tenant_id": "string",
  "order_id": "string",
  "status": "locked",
  "ordered_at": "ISO 8601",
  "locked_at": "ISO 8601",
  "enqueued_at": "ISO 8601"
}
```

**.Deduplication**: 同一 `order_id` のメッセージが複数回投入された場合、Azure Service Bus のメッセージ重複排除機能（Deduplication Window: 10 分）により重複を排除しなければならない。（BR-BATCH-09 参照）

**.TenantScope**: キュー投入時に `tenant_id` を必ず含め、バッチワーカーがテナントスコープを検証できるようにしなければならない。（BR-BATCH-02 参照）

---

### 2.2 Batch.Aggregate: バッチワーカーによる注文集約

**Batch.Aggregate.Worker: 常時稼働バッチワーカー**

**.AlwaysOn**: バッチワーカーは Azure Batch 上で常時稼働し、注文キューを継続的にポーリングしなければならない。スケジュール起動ではなく、キューにメッセージが存在する限り処理を継続する。

**.Pool**: システムは、Azure Batch の動的スケール Pool を使用し、キューのメッセージ数に応じてノード数を自動スケールしなければならない。（NFR-BATCH-03 参照）

**.TenantFactoryGroup**: バッチワーカーは、キューから取得したメッセージを `(tenant_id, factory_id)` の組み合わせ単位でメモリ上に集約しなければならない。

**Batch.Aggregate.FlushPolicy: フラッシュポリシー（バッチ生成タイミング）**

**.SizeFlush**: `(tenant_id, factory_id)` 単位の集約バッファが **1,000 件**（設定可能）に達した場合、即座に CSV 生成・転送処理を開始しなければならない。（BR-BATCH-01 参照）

**.TimeFlush**: 最初のメッセージが集約バッファに追加されてから **最大 30 分**（設定可能）が経過した場合、バッファの件数に関わらず CSV 生成・転送処理を開始しなければならない。（BR-BATCH-01 参照）

**.MinFlush**: 集約バッファが 1 件以上ある状態でフラッシュが発動した場合は、1 件からでも処理を実行しなければならない。

**.NodeAssignment**: 1 テナントのバッチ処理は 1 つの Azure Batch ノードに割り当て、複数テナントのデータを混在処理してはならない。（BR-BATCH-02 参照）

---

### 2.3 Batch.Extract: 注文データ抽出

**Batch.Extract.Query: テナント DB からの抽出**

**.Connect**: 各バッチ処理は、Azure Key Vault からテナント専用の DB 接続文字列を取得し、テナント専用 PostgreSQL DB に接続しなければならない。（BR-MT-51 参照）

**.FactoryOrderData**: システムは、集約バッファの `order_id` 一覧を条件として、テナント専用 DB の `factory_order_data` テーブルから工場送信用データ（注文ヘッダー・注文明細・配送先）を抽出しなければならない。`factory_order_data` は注文受付時点（EC サイト FR-001）に作成済みであるため、注文テーブルへの追加 JOIN は不要とする。

**.StatusCheck**: システムは、`factory_order_data` 抽出前に該当注文のステータスが `locked` であることを確認しなければならない。`locked` 以外の注文は処理をスキップしてログに記録する。

**.Count**: システムは、抽出した注文件数をバッチログに記録しなければならない。抽出件数が 0 件（キューメッセージに対応する注文が DB に存在しない）の場合は、バッチを正常完了とし、空ファイルを生成しない。

**Batch.Extract.StreamProcessing: 大量データの処理**

**.Streaming**: システムは、1,000 件以上のデータを一括メモリ展開せず、ストリーミング処理（Chunk 単位の SELECT）で抽出・変換しなければならない。

---

### 2.4 Batch.Transform: フォーマット変換

**Batch.Transform.FormatLookup: フォーマット定義の取得**

**.FormatDef**: システムは、各工場のフォーマット定義（列名・型・必須・マッピングルール・エンコーディング・区切り文字・ヘッダー有無）を Platform DB から取得しなければならない。

**Batch.Transform.Convert: 変換処理**

**.ColumnMapping**: システムは、フォーマット定義の `source` フィールドに基づいて、注文データの各フィールドを CSV の列にマッピングしなければならない。

**.TypeConversion**: システムは、フォーマット定義の `type` に応じて型変換（日付フォーマット変換・数値フォーマット変換・文字列トリム）を適用しなければならない。

**.Encoding**: システムは、フォーマット定義の `encoding`（例: UTF-8 / Shift_JIS）でファイルを出力しなければならない。

**.Header**: システムは、フォーマット定義の `has_header = true` の場合、列名ヘッダー行を先頭に出力しなければならない。

**フォーマット変換例（工場 A: Shift_JIS・カンマ区切り・ヘッダーあり）**:

入力（注文データ）:
```json
{
  "order_id": "myshop-20261201-00000001",
  "ordered_at": "2026-12-01T10:30:00+09:00",
  "product_code": "SKU-001",
  "product_name": "商品A",
  "quantity": 3,
  "unit_price": 1500
}
```

出力（CSV, Shift_JIS, カンマ区切り）:
```
受注番号,受注日,商品コード,商品名,数量,単価
myshop-20261201-00000001,20261201,SKU-001,商品A,3,1500
```

### 2.5 Batch.Validate: バリデーション

**Batch.Validate.Required: 必須項目チェック**

**.RequiredCheck**: システムは、フォーマット定義の `required = true` のフィールドが空でないことを検証しなければならない。空の場合はエラーとして記録し、該当行をエラーログに出力する。

**.TypeCheck**: システムは、型変換が失敗した行（例: 日付パース失敗）をエラーとして記録し、正常行の処理を継続しなければならない。

**.CountCheck**: システムは、変換完了後の正常件数・エラー件数をバッチログに記録しなければならない。エラー率が 5% を超えた場合はプラットフォーム管理者にアラートを送信しなければならない。

---

### 2.6 Batch.Load: Azure Blob への一時保存

**Batch.Load.Save: Blob 保存**

**.BlobPath**: システムは、変換した CSV ファイルをテナント専用 Blob コンテナの `batch/{YYYYMMDD}/{factory_code}/{batch_sequence}/` 配下に保存しなければならない。

**.FileName**: ファイル名は `{工場コード}_{テナントID}_{YYYYMMDD}_{バッチシーケンス番号}.csv` 形式とする（例: `FACTORY-A_tenant-001_20261201_003.csv`）。シーケンス番号は同一工場・同一日付で複数バッチが生成される場合に連番となる。（BR-FACTORY-03 参照）

**.Handoff**: Blob への保存完了後、システムは工場データ連携（FR-021）のジョブメッセージを Azure Service Bus の転送キュー（`factory-transfer-queue`）に投入し、転送処理に引き渡さなければならない。

**Batch.Load.Retention: 一時ファイルの保持期間**

**.TTL**: バッチで生成した一時 CSV ファイルは、工場への転送完了確認後 72 時間以内に Azure Blob から削除しなければならない。（BR-BATCH-08 参照）

---

### 2.7 Batch.Capture: 工場送信後の Stripe 決済確定

**Batch.Capture.Payment: Stripe PaymentIntent キャプチャ**

**.Trigger**: システムは、工場データ連携（FR-021）によるCSV転送完了通知を受け取った後、当該バッチに含まれる全注文の Stripe PaymentIntent キャプチャ（決済確定）をバッチ単位で実行しなければならない。（BR-EC-24 参照）

**.PerOrder**: システムは、注文ごとに `stripe_payment_intent_id` を使用して Stripe Capture API を呼び出し、実際の課金を確定しなければならない。

**.StatusUpdate**: キャプチャ成功後、システムは注文ステータスを `locked` から `confirmed` に更新しなければならない。`confirmed` 遷移と同時に消費者に注文確定メールを送信しなければならない。

**.CaptureFailed**: キャプチャが失敗した場合（カード有効期限切れ等）、システムはプラットフォーム管理者およびテナント管理者にアラートを送信しなければならない。注文ステータスは `capture_failed` に更新し、手動対応フローを起動しなければならない。

**.Idempotency**: 同一注文への重複キャプチャを防止するため、システムはキャプチャ実行前に注文ステータスが `locked` であることを確認しなければならない。

---

### 2.8 Batch.Monitor: 処理状況の監視

**Batch.Monitor.Metrics: Azure Monitor へのメトリクス送信**

**.Metrics**: システムは、以下のメトリクスを Azure Monitor にリアルタイムで送信しなければならない:
  - テナント ID
  - ジョブ ID
  - バッチシーケンス番号
  - 処理開始時刻
  - 処理済み件数
  - キュー残存メッセージ数
  - 進捗率（%）
  - エラー件数
  - 処理中の工場コード

**.QueueDepthAlert**: 注文キュー（`order-batch-queue`）のメッセージ滞留が **10,000 件**を超えた場合、プラットフォーム管理者に滞留アラートを送信しなければならない。（BR-BATCH-10 参照）

**.Dashboard**: プラットフォーム管理者は、Azure Monitor のダッシュボードで全テナントのキュー状況・バッチ処理状況をリアルタイムで確認できなければならない。

**.AdminDashboard**: テナント管理者は、管理サイトで自テナントの当日・直近 7 日間のバッチ実行状況（処理件数・処理バッチ数・最終処理時刻・エラー件数）を確認できなければならない。

---

### 2.8 Batch.Retry: 自動リトライ

**Batch.Retry.Auto: 自動リトライ処理**

**.RetryPolicy**: システムは、バッチジョブが失敗した場合、指数バックオフ（1 回目: 5 分後、2 回目: 10 分後、3 回目: 20 分後）で最大 3 回自動リトライしなければならない。（BR-BATCH-04 参照）

**.DeadLetter**: 3 回リトライ後も失敗した場合、該当メッセージを Azure Service Bus のデッドレターキューに移動し、プラットフォーム管理者とテナント管理者にアラートメールを送信しなければならない。（BR-BATCH-04 参照）

**.AlertOnFail**: アラートメール内容にはテナント ID・ジョブ ID・エラー内容・手動再実行手順を含める。

**.FailedStatus**: 最終失敗となったバッチは `failed` 状態に設定し、`batch_logs` テーブルに記録しなければならない。

**.OtherTenantsContinue**: 1 テナントのジョブが失敗しても、他テナントのキュー処理を継続しなければならない。（BR-BATCH-02 参照）

---

### 2.9 Batch.Complete: 完了確認・手動再実行

**Batch.Complete.ManualRerun: 手動再実行**

**.ManualTrigger**: プラットフォーム管理者は、テナント ID と対象期間を指定してバッチを手動再実行できなければならない。（BR-BATCH-07 参照）

**.Idempotency**: 手動再実行時を含め、同一 `order_id` を複数回処理した場合、工場に重複して送信してはならない。メッセージ重複排除とキュー再投入前のステータスチェックで保証する。（BR-BATCH-09 参照）

**.DeadLetterRequeue**: プラットフォーム管理者は、デッドレターキューのメッセージを確認し、管理コンソールから再キューイング（再処理）を実行できなければならない。

## 3. 処理フロー詳細

```
消費者が注文受付（EC サイト FR-001）
    │ Stripe オーソリ完了 → 注文ステータス: pending
    │ factory_order_data テーブルに工場送信用データ作成
    │ cancellation_cutoff_at 設定
    │
    ▼
キャンセル期限スケジューラー（1 分ごとに pending 注文をチェック）
    │ cancellation_cutoff_at 到達 → 注文ステータス: pending → locked
    │
    ▼
[1] Batch.Enqueue: Azure Service Bus order-batch-queue に注文イベント投入
    │ メッセージ: { event_id, tenant_id, order_id, status: "locked", locked_at, enqueued_at }
    │
    ▼
[2] Azure Batch Pool（常時稼働ワーカー）がキューをポーリング
    │ キューメッセージを (tenant_id, factory_id) 単位で集約バッファに追加
    │
    ├── フラッシュ発動条件（いずれかを満たした場合）:
    │    ├─ バッファが 1,000 件に達した（SizeFlush）
    │    └─ 最初のメッセージ追加から 30 分が経過（TimeFlush）
    │
    ▼
[3] Batch.Extract: factory_order_data テーブルから order_id 一覧で工場送信データを抽出
    │（Azure Key Vault から接続文字列を取得・テナント ID 検証）
    │
    ▼
[4] Batch.Transform: 工場マスタのフォーマット定義に基づいて CSV/TSV に変換
    │（エンコーディング・列定義・型変換を適用）
    │
    ▼
[5] Batch.Validate: バリデーション（必須項目・型チェック・件数確認）
    │
    ▼
[6] Batch.Load: テナント専用 Blob に保存
    │ パス: batch/{YYYYMMDD}/{factory_code}/{batch_sequence}/
    │ ファイル名: FACTORY-A_tenant-001_20261201_003.csv
    │
    ▼
[7] factory-transfer-queue に転送ジョブメッセージを投入
    │ → FR-021（工場データ連携）が受け取り、SFTP/Blob 転送を実行
    │
    ▼
[8] Batch.Capture: FR-021 転送完了通知を受信
    │ → Stripe PaymentIntent キャプチャ（決済確定）をバッチ内全注文に実行
    │ → 注文ステータス: locked → confirmed
    │ → 消費者に注文確定メール送信
    │
    ▼
Batch.Monitor: Azure Monitor にメトリクスを随時送信
    │
    │ 失敗の場合 ──→ Batch.Retry（最大 3 回）──→ Dead Letter キュー ──→ アラート
```

## 4. フラッシュポリシーとバッチ生成の例

同一テナント・工場 A に対して当日中に以下の順序でバッチが生成される例:

```
09:00〜09:30: 注文 800 件が order-batch-queue に投入
  → 09:30 に TimeFlush 発動（30 分経過） → バッチ #001 生成・転送（800 件）

10:00〜10:15: 注文 1,200 件が集中投入
  → 10:15 に SizeFlush 発動（1,000 件到達） → バッチ #002 生成・転送（1,000 件）
  → 10:45 に TimeFlush 発動（残り 200 件）  → バッチ #003 生成・転送（200 件）

23:00〜23:50: 注文 50 件（閑散期）
  → 23:50 に TimeFlush 発動（30 分経過）   → バッチ #012 生成・転送（50 件）
```

| 指標 | 要件値 | 根拠 |
|------|-------|------|
| キュー投入からバッチ生成（最大遅延） | 30 分以内 | BR-BATCH-01（TimeFlush） |
| バッチ生成から工場への転送完了 | 30 分以内 | NFR-FACTORY-03 |
| テナントあたり最大注文件数（日次） | 100 万件/日 | AS-3 |
| キュー滞留アラートしきい値 | 10,000 件 | BR-BATCH-10 |

| Azure Batch ノード数 | 動的スケール（キュー深度に応じて自動調整） | NFR-BATCH-03 |

## 6. バッチログ記録項目

バッチ処理ごとに `batch_logs` テーブルに記録する項目:

| フィールド | 型 | 説明 |
|---------|----|----|
| log_id | UUID | ログ一意識別子 |
| tenant_id | UUID | テナント ID |
| batch_date | DATE | バッチ対象日（JST） |
| batch_sequence | INTEGER | 同一日・同一工場内の連番 |
| job_id | VARCHAR(100) | Azure Batch ジョブ ID |
| factory_id | UUID | 工場 ID |
| flush_reason | ENUM | size_flush / time_flush / manual |
| extract_count | INTEGER | 抽出した注文件数 |
| success_count | INTEGER | 正常処理した注文件数 |
| error_count | INTEGER | エラーとなった注文件数 |
| started_at | TIMESTAMPTZ | バッチ開始時刻（JST） |
| completed_at | TIMESTAMPTZ | バッチ完了時刻（JST） |
| status | ENUM | success / failed / running / retry |
| error_message | TEXT | エラー詳細（失敗時） |
