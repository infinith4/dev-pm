## 1. 概要

| 項目 | 内容 |
|------|------|
| アクター（主） | 工場システム（外部）─ 出荷完了後に ShopHub に Webhook POST を送信 |
| アクター（更新） | ShopHub SaaS システム─ 注文ステータス更新・消費者通知 |
| アクター（確認） | 消費者─ 発送通知メールを受信 |
| アクター（確認） | 店舗スタッフ（テナント管理者）─ 管理サイトで出荷状況を確認 |
| 目的 | 工場が CSV データを受け取り数時間後に出荷を完了したら、Webhook で ShopHub に通知し、注文ステータスを `shipped` に更新し、消費者に発送通知メールを送信する |
| スコープ | 工場出荷完了通知受信（Webhook 受信）・注文ステータス更新・消費者メール通知 |
| レベル | サブファンクション（システムレベル） |
| 頻度 | 工場の出荷タイミングに応じて随時（通常は夜間バッチ後数時間以内、日中に集中） |

---

## 2. 事前条件

- FR-021（工場データ連携）により、工場に注文データが送信済みである
- 工場マスタに `ship_notify_enabled = true` が設定されており、HMAC キーが Azure Key Vault に登録されている
- 工場システムが ShopHub の通知受信 URL と HMAC キーを保有している
- 対象注文が Tenant DB に存在し、ステータスが `confirmed` または `processing` である

---

## 3. 事後条件

**成功時**:
- 通知に含まれるすべての注文のステータスが `shipped` に更新されている
- `orders.shipped_at` に工場からのペイロードの `shipped_at` 日時が記録されている
- 追跡番号・配送業者が指定された場合は `order_shipping_info` テーブルに記録されている
- 消費者に発送通知メールが送信されている
- 管理サイトの注文一覧にリアルタイムで反映されている
- `ship_notify_logs` テーブルに受信ログが記録されている

**一部スキップ時**:
- すでに `shipped` 状態の注文はスキップされ、ログに記録される
- 存在しない `order_id` はスキップされ、レスポンスの `skipped_order_ids` に含まれる

---

## 4. トリガー

工場システムが出荷作業を完了し、ShopHub の通知受信エンドポイントに HTTPS POST リクエストを送信した

---

## 5. 正常フロー

| ステップ | アクター | 動作 |
|---------|---------|------|
| 1 | 工場システム | FR-021 で受け取った CSV データを元に出荷作業を実施。出荷完了後（通常数時間以内）、ShopHub の通知受信エンドポイントに HTTPS POST で出荷完了通知を送信する。リクエストヘッダーに HMAC-SHA256 署名を付与する。（BR-FACTORY-12） |
| 2 | Azure APIM | HTTPS リクエストを受信し、通知受信エンドポイント（`/api/v1/factories/{factory_id}/ship-notify`）にルーティングする。 |
| 3 | ShipNotify.Receive | JSON ペイロードのスキーマ（`factory_code`・`tenant_id`・`shipped_orders`）を検証する。スキーマ不正の場合は HTTP 400 を返す。 |
| 4 | ShipNotify.Receive | リクエストヘッダー `X-ShopHub-Signature` の HMAC-SHA256 値を Azure Key Vault から取得した工場の HMAC キーで検証する。不一致の場合は HTTP 401 を返す。（BR-FACTORY-12） |
| 5 | ShipNotify.Receive | ペイロードの `tenant_id` が URL の `factory_id` に紐づくテナントと一致することを検証する。不一致の場合は HTTP 403 を返す。（BR-FACTORY-13） |
| 6 | ShipNotify.Receive | `shipped_orders` の各 `order_id` について、既に `shipped` 状態でないことを確認する（冪等性チェック）。（BR-FACTORY-14） |
| 7 | ShipNotify.Update | 検証済みの各注文のステータスを `shipped` に更新し、`shipped_at` を記録する。追跡番号・配送業者が含まれる場合は `order_shipping_info` テーブルに記録する。（BR-FACTORY-15） |
| 8 | ShipNotify.ConsumerAlert | 更新された各注文の消費者に発送通知メール（テナントブランド名・注文番号・出荷日時・追跡番号・配送先）を送信する。（BR-FACTORY-15） |
| 9 | ShipNotify.StaffAlert | 管理サイトの注文一覧にリアルタイムで出荷状況を反映し、ログイン中の店舗スタッフに通知バナーを表示する。 |
| 10 | ShipNotify.Log | `ship_notify_logs` テーブルに受信ログ（工場 ID・受信日時・件数・成功/スキップ/エラー件数）を記録する。 |
| 11 | ShipNotify.Endpoint | 工場システムに HTTP 200 レスポンス（成功・スキップ件数を含む JSON）を返す。 |
| 12 | 消費者 | 発送通知メールを受信し、追跡番号で配送状況を確認できる。 |
| 13 | 店舗スタッフ | 管理サイトで注文ステータスが `shipped` になっていることを確認する。 |

---

## 6. 代替フロー

### 代替フロー A: 一部注文がスキップ（既処理または存在しない order_id）

| ステップ | 説明 |
|---------|------|
| A-6 | `order_id` が既に `shipped` 状態、または Tenant DB に存在しない場合、当該行をスキップする。 |
| A-7〜A-10 | 残りの有効な注文は正常フローで処理を継続する。 |
| A-11 | HTTP 200 レスポンスに `skipped_order_ids` として除外された注文 ID を含める。 |

### 代替フロー B: 追跡番号なしの通知

| ステップ | 説明 |
|---------|------|
| B-7 | `tracking_number` が含まれない場合、`order_shipping_info` への追跡情報記録をスキップする。 |
| B-8 | 発送通知メールは追跡番号の記載を省略して送信する。 |
| B-11 | 正常フローと同様に HTTP 200 を返す。 |

### 代替フロー C: 複数工場から同日に通知

| ステップ | 説明 |
|---------|------|
| C-1 | 工場 A と工場 B が同日に独立して通知を送信する。 |
| C-2〜C-11 | 各工場の通知は独立して処理される（工場 A の通知処理が工場 B の処理をブロックしない）。 |

## 7. 例外フロー

### 例外 E-1: HMAC 署名不一致（不正アクセス）

| 条件 | `X-ShopHub-Signature` の検証が失敗する |
|------|------|
| システムの動作 | HTTP 401 を返す。不正アクセスとして Azure Monitor にセキュリティアラートを記録する。同一 IP から 10 回失敗した場合、プラットフォーム管理者に通知する |
| 事後状態 | 注文ステータスは更新されない。テナント管理者が HMAC キーの再発行を検討する |

### 例外 E-2: テナント・工場の不一致（誤送信）

| 条件 | ペイロードの `tenant_id` が工場マスタのテナントと一致しない |
|------|------|
| システムの動作 | HTTP 403 を返す。クロステナント誤送信として Azure Monitor に記録する（BR-FACTORY-13） |
| 事後状態 | 注文ステータスは更新されない。工場システムの設定を確認するようテナント管理者に通知する |

### 例外 E-3: メール送信失敗

| 条件 | 消費者への発送通知メール送信が失敗する（SMTP エラー等） |
|------|------|
| システムの動作 | 注文ステータスの更新は確定させる（メール送信失敗は注文更新をロールバックしない）。メール送信をキューに保持し、5 分後・10 分後・20 分後に最大 3 回リトライする |
| 事後状態 | 3 回リトライ後も失敗した場合、テナント管理者にアラートを送信する。管理サイトからの手動再送信を可能にする |

### 例外 E-4: 高頻度エラー（工場システムの不具合）

| 条件 | 同一工場から 1 時間以内に 10 件以上のエラー通知が発生する |
|------|------|
| システムの動作 | テナント管理者にアラートメール（工場名・エラー件数・エラー内容）を送信する |
| 事後状態 | テナント管理者が工場システムのエラーを調査・対応する |

---

## 8. 工場出荷完了通知タイムライン

```
（前日 22:00〜翌 04:00 JST）
夜間バッチ完了 → 工場に CSV ファイル転送（FR-021）
    │
    ▼
（当日 午前中〜午後）
工場システムが CSV を取り込み、製造・出荷準備を実施（数時間）
    │
    ▼
（出荷完了タイミング: 例 10:00〜16:00 JST）
工場システムが出荷完了通知を HTTPS POST で送信
    │
    ▼
ShopHub が通知を受信・検証（5 秒以内）
    │
    ├─ 注文ステータスを shipped に更新
    ├─ 消費者に発送通知メール送信（1 分以内）
    └─ 管理サイトにリアルタイム反映
    │
    ▼
消費者が発送通知メールを受信・追跡番号で配送確認
```
