## 1. 概要

| 項目 | 内容 |
|------|------|
| アクター | 消費者（CIAM 認証済み、またはゲスト） |
| 目的 | EC サイトで商品を選択し、Stripe 決済で購入を完了する |
| スコープ | テナント専用 EC サイト（`shop.{顧客ドメイン}`） |
| レベル | ユーザーゴール |
| 頻度 | 日次 100 万件（全テナント合計） |

---

## 2. 事前条件

- テナントが EC サイトを公開している（テナント状態: `active`）
- 購入対象商品が在庫あり（`stock_qty > 0`）の状態で登録されている
- テナントの Stripe 課金設定が有効である
- CIAM 認証済み消費者の場合: テナント専用 CIAM にアカウントが存在する

---

## 3. 事後条件

**成功時**:
- 注文が `confirmed` 状態でテナント DB に保存される
- 在庫が注文数量分減算される
- Stripe に Payment Intent が成功状態で記録される
- 消費者に注文確認メール（注文番号・商品・合計・配送先）が送信される
- 当日夜の夜間バッチ（FR-020）の処理対象に含まれる

**失敗時**:
- 在庫仮確保が解除される
- カートの内容は維持される
- 消費者にエラーの理由が表示される

---

## 4. トリガー

消費者が EC サイト（`shop.{顧客ドメイン}`）のチェックアウトボタンをクリックした

---

## 5. 正常フロー

| ステップ | 消費者の操作 | システムの動作 |
|---------|-----------|------------|
| 1 | テナントの EC サイト URL（`shop.myshop.jp`）にアクセス | Azure Front Door がホスト名からテナント A を識別してルーティング |
| 2 | （未ログインの場合）「ログイン」または「ゲスト購入」を選択 | テナント A の CIAM ログインページを表示 |
| 3 | CIAM メール認証またはソーシャルログイン（Google）でログイン | CIAM が JWT を発行。JWT の `iss` クレームにテナント A の Entra ID テナント ID が含まれる |
| 4 | 商品カタログから商品を検索・閲覧 | Azure Cognitive Search（テナント A のインデックス）で商品を検索して表示 |
| 5 | 商品詳細ページで「カートに追加」をクリック | 在庫数チェック → Redis にカートデータを保存 |
| 6 | カートページで内容を確認し「購入手続きへ」をクリック | カートサマリー（商品・数量・小計・送料・合計）を表示 |
| 7 | 配送先住所を入力（または過去の住所を選択） | 送料を計算して合計金額を更新 |
| 8 | Stripe のカード入力フォームにクレジットカード情報を入力 | Stripe Elements がカード情報をブラウザから直接 Stripe へ送信（システムにカード情報は渡らない） |
| 9 | 「注文を確定する」ボタンをクリック | 在庫を仮確保 → Stripe Payment Intent を実行 |
| 10 | — | Stripe 決済成功 → 在庫を確定（減算） → 注文を `confirmed` で DB に保存 → 注文番号生成（`myshop-20261201-00000001`） |
| 11 | 注文完了ページが表示される | 注文確認メールを消費者に送信 |
| 12 | — | 当日 22:00 の夜間バッチ（FR-020）の対象として自動的に処理される |

---

## 6. 代替フロー

### 代替フロー A: ゲスト購入

| ステップ | 説明 |
|---------|------|
| A-2 | 消費者が「ゲストとして購入」を選択 |
| A-3 | メールアドレスのみ入力（CIAM アカウント作成不要） |
| A-4〜A-11 | 正常フローと同様。注文確認メールをゲストのメールアドレスに送信 |
| A-12 | ゲスト購入後に CIAM アカウント作成を促すメールを送信 |

### 代替フロー B: ソーシャルログイン（Google）

| ステップ | 説明 |
|---------|------|
| B-2 | 消費者が「Google でログイン」ボタンをクリック |
| B-3 | CIAM が Google OAuth 2.0 フローを起動 → Google 認証完了後 CIAM が JWT を発行 |
| B-4〜B-12 | 正常フローと同様 |

### 代替フロー C: 過去の配送先を使用

| ステップ | 説明 |
|---------|------|
| C-7 | CIAM ログイン済みの場合、過去の配送先住所一覧から選択可能 |
| C-8〜C-12 | 正常フローと同様 |

## 7. 例外フロー

### 例外 E-1: 在庫切れ

| 条件 | カートへの追加時に `stock_qty = 0` |
|------|------|
| システムの動作 | カートへの追加を拒否し「在庫切れ」メッセージを表示 |
| 事後状態 | 商品がカートに追加されない。消費者はカートページへ戻れる |

### 例外 E-2: 決済失敗（カードエラー）

| 条件 | Stripe Payment Intent が失敗 |
|------|------|
| システムの動作 | 在庫仮確保を解除。カードエラーの理由を表示（例: 「カードが拒否されました。別のカードをお試しください」）。カートの内容を維持 |
| 事後状態 | 注文は作成されない。消費者はカード情報を修正して再試行できる |

### 例外 E-3: 在庫確保タイムアウト

| 条件 | 在庫仮確保から 10 分以内に決済が完了しない |
|------|------|
| システムの動作 | 在庫仮確保を解除。消費者にタイムアウトのメッセージを表示してカートページへ戻す |
| 事後状態 | 注文は作成されない。カートは維持されているが在庫が他者に購入された可能性を案内 |

### 例外 E-4: CIAM 認証エラー

| 条件 | CIAM への接続失敗・ログインエラー |
|------|------|
| システムの動作 | ログインエラーメッセージを表示。ゲスト購入の案内を表示 |
| 事後状態 | 消費者はゲスト購入に切り替えることができる |

### 例外 E-5: テナント間データ分離違反（検知時）

| 条件 | JWT の `iss` クレームがリクエストのテナントと不一致 |
|------|------|
| システムの動作 | HTTP 401 を返す。Azure Monitor にセキュリティアラートを記録 |
| 事後状態 | リクエストは処理されない。プラットフォーム管理者に通知 |

---

## 8. 補足情報

- **テナント分離**: 消費者のセッション JWT は Entra ID テナント固有の `iss` クレームを持ち、テナント A の JWT でテナント B の商品を購入しようとしても拒否される
- **夜間バッチとの連携**: 正常に完了した注文（`confirmed` / `shipped`）は当日 22:00 に自動起動する夜間バッチ（FR-020）で工場へのデータ送信対象となる
- **ピーク対応**: Azure Front Door + Azure Container Apps Auto Scaling で 10,000 req/sec に対応
