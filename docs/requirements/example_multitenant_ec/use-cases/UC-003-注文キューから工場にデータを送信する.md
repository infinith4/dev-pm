## 1. 概要

| 項目 | 内容 |
|------|------|
| アクター（主） | Azure Service Bus（注文イベントキュー） |
| アクター（監視） | プラットフォーム管理者（キュー・バッチ状況の監視・障害対応） |
| アクター（受信） | 工場システム（各工場の SFTP サーバー / Azure Blob） |
| 目的 | 注文が確定するたびにキューに投入し、常時稼働のバッチワーカーが注文を集約・CSV に変換して工場に送信する。送信タイミングは件数（1,000 件）または時間（30 分）のいずれかのしきい値に達したタイミング。 |
| スコープ | 注文キュー駆動バッチ処理（Azure Batch）・工場データ連携（SFTP/Blob 転送） |
| レベル | サブファンクション（システムレベル） |
| 頻度 | 注文確定のたびにキュー投入（随時）。バッチ生成は SizeFlush（1,000 件）または TimeFlush（30 分）ごと |

---

## 2. 事前条件

- Professional または Enterprise プランで `active` 状態のテナントが 1 件以上存在する
- 対象テナントに 1 件以上の工場設定（工場マスタ）が登録されている
- 工場マスタにフォーマット定義が設定されている
- 工場の SFTP サーバーまたは Azure Blob が利用可能な状態である
- Azure Batch Pool が起動可能な状態（ノードが利用可能）である
- `order-batch-queue`（Azure Service Bus）が稼働中である

---

## 3. 事後条件

**成功時**:
- キューに投入された注文が集約・CSV に変換され、工場ごとのファイルとして Blob に保存されている
- ファイルが SFTP または Azure Blob に転送されている
- 転送ログ（件数・ファイルサイズ・転送先・完了時刻）が記録されている
- 工場システムに転送完了通知（Webhook / メール）が送信されている
- `batch_logs` テーブルに実行ログが記録されている

**一部失敗時**:
- 失敗したバッチがデッドレターキューに移動され、`failed` 状態として記録されている
- プラットフォーム管理者とテナント管理者にアラートメールが送信されている
- 他テナント・他工場の処理は正常に継続している

---

## 4. トリガー

消費者が注文を確定（`confirmed`）または出荷済み（`shipped`）にし、注文イベントが Azure Service Bus キューに投入された

---

## 5. 正常フロー

| ステップ | アクター | 動作 |
|---------|---------|------|
| 1 | EC サイト（FR-001） | 消費者が注文を確定する。注文ステータスが `confirmed` または `shipped` に遷移する。 |
| 2 | Batch.Enqueue | 注文確定イベントメッセージ（tenant_id・order_id・status・enqueued_at）を `order-batch-queue` に投入する。Azure Service Bus の重複排除機能により同一 order_id の重複投入を防止する。（BR-BATCH-01, BR-BATCH-09） |
| 3 | Azure Batch Pool（常時稼働） | キューをポーリングし、メッセージを (tenant_id, factory_id) 単位で集約バッファに追加する。キューが空でも常時稼働し、次のメッセージを待機する。（BR-BATCH-02） |
| 4 | Batch.Aggregate（フラッシュ判定） | 集約バッファが **1,000 件**に達した場合（SizeFlush）、または最初のメッセージ追加から **30 分**が経過した場合（TimeFlush）、CSV 生成処理を開始する。（BR-BATCH-01） |
| 5 | Batch.Extract | Azure Key Vault からテナント専用 DB 接続文字列を取得する。テナント ID を検証後、テナント専用 PostgreSQL DB から集約バッファの order_id 一覧に対応する注文データ（注文ヘッダー・注文明細）を抽出する。（BR-MT-51） |
| 6 | Batch.Transform | 工場マスタのフォーマット定義（列名・型・エンコーディング・区切り文字・ヘッダー）に基づいて注文データを CSV/TSV に変換する。（BR-FACTORY-01） |
| 7 | Batch.Validate | 変換後データのバリデーション（必須項目・型チェック・件数確認）を実施する。エラー行はスキップして処理を継続する。 |
| 8 | Batch.Load | 変換済み CSV ファイルをテナント専用 Blob コンテナの `batch/{YYYYMMDD}/{factory_code}/{batch_sequence}/` に保存する。バッチシーケンス番号（当日の工場別連番）を付与する。 |
| 9 | Batch.Load | 処理状況（処理件数・バッチシーケンス・エラー件数）を Azure Monitor に送信する。 |
| 10 | 工場データ連携 | `factory-transfer-queue` に転送ジョブメッセージを投入。FR-021 が受け取り、工場マスタの転送方式に応じて処理: **SFTP**: Key Vault から SSH 秘密鍵を取得し SFTP サーバーへ転送。**Blob**: 工場マスタの Blob URI にファイルを配置し SAS URL を生成。 |
| 11 | 工場データ連携 | 転送結果（件数・ファイルサイズ・転送先・完了時刻・ステータス）を `transfer_logs` テーブルに記録する。（BR-FACTORY-04） |
| 12 | 工場データ連携 | 工場マスタの通知設定に基づいて転送完了通知（Webhook POST またはメール）を工場システムに送信する。（BR-FACTORY-08） |
| 13 | 工場システム | SFTP からファイルをダウンロード、または Blob の SAS URL でファイルを取得して製造準備を開始する。 |

## 6. 代替フロー

### 代替フロー A: SizeFlush による即時バッチ生成

| ステップ | 説明 |
|---------|------|
| A-3〜A-4 | 注文が短時間に集中し、集約バッファが 1,000 件に達する。TimeFlush（30 分）を待たずに即座にフラッシュが発動する。 |
| A-5〜A-13 | 正常フロー 5〜13 と同様に処理。残りのメッセージは次のフラッシュサイクルで処理される。 |

### 代替フロー B: 同日中に複数バッチが生成される（工場 A の例）

| ステップ | 説明 |
|---------|------|
| B-8 | 同一テナント・同一工場に対して当日中に複数回 TimeFlush/SizeFlush が発動し、バッチ #001・#002・#003 ... と連番でファイルが生成される。 |
| B-10〜B-12 | 各バッチは独立して転送される。工場システムは複数ファイルをそれぞれ取得して処理する。 |

### 代替フロー C: Blob 転送（工場 C）

| ステップ | 説明 |
|---------|------|
| C-10 | 工場 C の転送方式が `blob` の場合、SFTP の代わりに Azure Blob へファイルを配置し、SAS URL（有効期限 7 日）を生成する。 |
| C-12 | Webhook で工場 C に SAS URL を含む転送完了通知を送信する。 |

### 代替フロー D: 手動再実行

| ステップ | 説明 |
|---------|------|
| D-0 | プラットフォーム管理者が管理コンソールから手動再実行を指示（テナント ID・対象日・工場 ID を指定）。（BR-BATCH-07） |
| D-1 | バッチワーカーが指定条件に一致する注文を order-batch-queue に再投入する。冪等性チェックにより既処理の order_id は重複送信されない。（BR-BATCH-09） |
| D-2〜D-13 | 正常フロー 4〜13 と同様に処理。 |

## 7. 例外フロー

### 例外 E-1: キュー滞留（バッチワーカーが処理に追いつかない）

| 条件 | `order-batch-queue` のメッセージ滞留が 10,000 件を超える |
|------|------|
| システムの動作 | Azure Monitor がキュー深度を検知し、プラットフォーム管理者に滞留アラートを送信する。（BR-BATCH-10）。Azure Batch Pool がノードを自動スケールアウトして処理能力を増強する。（NFR-BATCH-03） |
| 事後状態 | スケールアウト後に処理が追いつく。それでも滞留が続く場合はプラットフォーム管理者が手動でノード数を増加させる |

### 例外 E-2: バッチ処理失敗（DB 接続エラー・変換エラー等）

| 条件 | Batch.Extract または Batch.Transform が失敗する |
|------|------|
| システムの動作 | 指数バックオフで 3 回自動リトライする（5 分・10 分・20 分後）。（BR-BATCH-04）。3 回失敗でデッドレターキューに移動し、プラットフォーム管理者とテナント管理者にアラートメールを送信する |
| 事後状態 | 管理コンソールからデッドレターキューを確認し、原因解決後に手動再キューイングを実施する |

### 例外 E-3: SFTP 接続失敗

| 条件 | 工場の SFTP サーバーへの接続が失敗する |
|------|------|
| システムの動作 | FR-021 の Factory.Retry が指数バックオフで 3 回自動リトライする（1 分・2 分・4 分後）。（BR-FACTORY-05）。3 回失敗でプラットフォーム管理者とテナント管理者にアラートメールを送信。転送ログに `failed` を記録 |
| 事後状態 | テナント管理者が SFTP 設定を確認後、手動再転送を実行する |

### 例外 E-4: フォーマット変換エラー（データ品質問題）

| 条件 | 注文データの必須フィールドが NULL / 型変換が失敗 |
|------|------|
| システムの動作 | エラー行をスキップして処理を継続する。エラー件数をバッチログに記録する。エラー率が 5% を超えた場合はプラットフォーム管理者にアラートを送信する |
| 事後状態 | 正常行のみを含む CSV ファイルが生成・転送される。テナント管理者にエラー件数と対象注文番号が通知される |

### 例外 E-5: テナント A のジョブがテナント B のデータにアクセス試みる

| 条件 | バッチジョブが自テナント以外の DB 接続文字列を使用しようとする |
|------|------|
| システムの動作 | Azure Key Vault のアクセスポリシーにより接続を拒否する。セキュリティアラートを Azure Monitor に記録する。当該ジョブを `failed` に設定する |
| 事後状態 | データ分離は維持される。プラットフォーム管理者がインシデント調査を実施する |

## 8. キュー駆動バッチ処理タイムライン（例）

```
（09:00）
注文が確定 → order-batch-queue に投入（随時）
    │
    ▼
（09:00〜09:30）
バッチワーカーが集約バッファに追加（800 件蓄積）
    │
    ▼
（09:30: TimeFlush 発動）
FACTORY-A_tenant-001_20261201_001.csv 生成・転送・通知
    │
    ▼
（10:00〜10:15）
注文が集中投入（1,200 件）→ 10:15 に SizeFlush 発動（1,000 件）
FACTORY-A_tenant-001_20261201_002.csv 生成・転送・通知
    │ 残り 200 件は次のバッファへ
    ▼
（10:45: TimeFlush 発動 ─ 残り 200 件）
FACTORY-A_tenant-001_20261201_003.csv 生成・転送・通知
    │
    ▼
（以降、SizeFlush / TimeFlush のタイミングで随時バッチ生成・転送）
    │
    ▼
工場システムが CSV を受け取り次第、製造準備・出荷作業を開始
→ 出荷完了後に FR-022（工場出荷完了通知受信）で ShopHub に通知
```
